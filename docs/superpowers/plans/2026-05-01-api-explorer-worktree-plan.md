# 轻量 API Explorer 与 Worktree 开发模式实施计划

## 1. 计划目标

本计划用于承接已确认的设计文档 [2026-05-01-api-explorer-worktree-design.md](file:///Users/bytedance/Desktop/MyWork/github/qq-music-api/docs/superpowers/specs/2026-05-01-api-explorer-worktree-design.md)，将“项目启动后自动打开可视化接口测试页面，并通过 `git worktree` 模式实施”拆解为可执行、可验证、可回滚的实施步骤。

本计划重点解决三件事：

1. 在独立 `git worktree` 中开展后续开发，避免污染当前主工作区。
2. 为当前 Koa 项目增加一个轻量、可输入参数的本地 API Explorer。
3. 让开发启动流程在非测试环境下自动打开该 Explorer 页面，并补齐测试与验证。

## 2. 实施原则

- 先隔离后开发：任何功能代码改动都在新的 `git worktree` 中完成。
- 先最小可用再扩展：首版只做接口选择、参数输入、请求发送和结果展示。
- 先可测试再接入：优先抽离元数据与 URL 构造逻辑，避免把逻辑全部塞进静态页面脚本。
- 先保护现有行为：不破坏现有 API 路由、响应格式和测试环境约束。
- 先验证副作用边界：自动打开浏览器仅在开发模式启用，测试环境必须禁用。

## 3. 交付范围

本次实施计划覆盖以下交付物：

- 新建 `git worktree` 与功能分支
- 集中式接口元数据模块
- Explorer 静态页面和配套脚本
- Explorer 页面托管接入
- 开发启动自动打开浏览器能力
- 对应单元测试、必要的集成验证和使用说明更新

本计划不覆盖：

- 全量 OpenAPI Schema 生成
- 完整前端工程化重构
- 生产环境在线文档发布

## 5. 分阶段实施步骤

## 阶段 1：创建 Worktree 并准备开发基线

### 目标

建立独立开发目录，确保当前主工作区保持不变。

### 执行动作

1. 从当前仓库创建新分支，例如 `feat/api-explorer`。
2. 使用 `git worktree add` 创建独立工作目录，例如 `../qq-music-api-api-explorer`。
3. 在新目录内安装依赖。
4. 在新目录中执行一次基线检查：
   - `npm run lint`
   - `npm test`
5. 记录基线结果，确保后续问题可归因到本次改动。

### 产出

- 可独立开发的 worktree
- 基线验证记录

### 风险

- 当前主工作区存在未提交改动，可能影响新分支创建时的基点选择。

### 应对

- 使用当前 `HEAD` 创建 worktree，但后续所有功能开发仅在新 worktree 中进行。
- 不在当前主工作区继续修改功能代码。

## 阶段 2：建立 Explorer 接口元数据与工具层

### 目标

把接口描述抽离成可驱动页面的集中式配置，并建立 URL 构造等纯逻辑工具，方便测试。

### 执行动作

1. 新增接口元数据模块，建议路径：
   - `src/config/api-explorer.ts` 或
   - `src/constants/api-explorer.ts`
2. 为每个首批纳入 Explorer 的接口定义：
   - 基本信息
   - 路径参数
   - 查询参数
   - 请求体字段
   - 示例值
3. 首批优先覆盖高价值接口：
   - `getHotkey`
   - `getSearchByKey`
   - `getLyric`
   - `getAlbumInfo`
   - `batchGetSongInfo`
   - `batchGetSongLists`
4. 抽离 URL 构造和参数处理工具函数，例如：
   - 路径模板替换
   - 空查询参数过滤
   - `GET` / `POST` 请求配置生成
5. 为元数据和工具函数补齐单元测试。

### 产出

- 集中式接口元数据模块
- URL 构造与参数处理工具
- 对应单元测试

### 完成标准

- 无需在页面脚本中硬编码接口结构
- 工具函数覆盖正例、反例和边界条件

## 阶段 3：实现 Explorer 页面最小可用版本

### 目标

完成可视化调试页面的首版闭环。

### 执行动作

1. 新增 Explorer 静态页面资源。
2. 页面至少包含以下模块：
   - 接口列表
   - 参数表单
   - 请求预览
   - 响应展示
3. 页面支持以下基础行为：
   - 切换接口
   - 根据接口元数据渲染输入项
   - 对必填项做基础校验
   - 发起请求
   - 展示状态码、耗时、返回体
4. 页面默认请求目标指向本地 API 服务地址。
5. 对空状态、请求失败和服务未启动场景提供明确提示。

### 产出

- Explorer 页面资源
- 页面脚本
- 基础样式

### 完成标准

- 首版页面可以独立完成至少两个接口调试场景

## 阶段 4：接入 Koa 静态托管与访问入口

### 目标

让 Explorer 页面可由本项目直接访问，并具备稳定入口。

### 执行动作

1. 确认 Explorer 页面托管目录。
2. 在 `src/app.ts` 中接入静态资源访问路径，或复用现有静态目录。
3. 约定本地访问地址，例如：
   - `http://localhost:3200/explorer`
4. 如有必要，增加一个重定向或入口页。
5. 在 `docs/` 文档中补充 Explorer 使用说明和入口链接。

### 产出

- 稳定的本地 Explorer 访问地址
- 更新后的使用文档

### 完成标准

- 启动 API 后手工访问 Explorer 地址可打开页面

## 阶段 5：接入自动打开浏览器能力

### 目标

在开发启动时自动打开 Explorer，同时不影响测试与 CI。

### 执行动作

1. 新增浏览器打开能力封装，避免直接把平台命令散落在 `app.ts`。
2. 判断当前环境是否允许自动打开：
   - 非 `test`
   - 非 CI
   - 可通过环境变量显式关闭
3. 在开发启动链路中调用自动打开逻辑。
4. 对自动打开失败场景做容错：
   - 记录日志
   - 不中断服务启动
5. 若当前 `npm run dev` 不便直接编排该逻辑，则新增启动脚本，例如：
   - `npm run dev:explorer`
   - 或统一替换 `npm run dev`

### 产出

- 浏览器自动打开封装
- 启动脚本或启动流程改造
- 自动打开能力测试

### 完成标准

- 启动开发命令后，浏览器自动打开 Explorer
- 测试环境不会触发打开行为

## 8. 测试计划

### 单元测试

重点验证：

- 参数元数据定义完整性
- 路径参数替换逻辑
- 查询参数序列化逻辑
- `GET` 与 `POST` 请求配置逻辑
- 自动打开开关条件判断

### 集成测试

重点验证：

- Explorer 静态资源能被 Koa 正常访问
- 入口地址返回预期页面资源

### 功能测试

手工验证步骤：

1. 执行开发启动命令
2. 确认浏览器自动打开 Explorer
3. 通过 `getHotkey` 或 `getSearchByKey` 发起 `GET` 请求
4. 通过 `batchGetSongInfo` 或 `batchGetSongLists` 发起 `POST` 请求
5. 确认响应区能展示状态码和 JSON 返回体

### 覆盖率策略

- 优先覆盖纯逻辑模块，快速提升稳定覆盖率
- 页面脚本中的复杂逻辑尽量抽离成可测试函数
- 避免依赖真实外部接口导致测试波动

## 9. 风险与回退策略

### 风险 1：静态页面和 Koa 集成成本高于预期

回退方案：

- 暂时改为双服务模式，由 docsify 提供 Explorer 页面
- 先保证功能可用，再决定是否合并为单服务

### 风险 2：自动打开浏览器在不同环境下兼容性不一致

回退方案：

- 保留手工访问地址
- 自动打开能力通过环境变量可关闭

### 风险 3：页面脚本难测

回退方案：

- 把核心逻辑抽离成纯函数模块
- 只对页面 DOM 交互保留最小集成验证

### 风险 4：覆盖率无法一次达到目标

回退方案：

- 优先补足元数据、工具层和启动逻辑测试
- 再针对新增代码空白区域补高价值测试
