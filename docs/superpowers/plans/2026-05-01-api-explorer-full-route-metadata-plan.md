# API Explorer 全量路由元数据扩展实施计划

## 1. 计划目标

本计划承接已确认的设计文档 [2026-05-01-api-explorer-full-route-metadata-design.md](file:///Users/bytedance/Desktop/MyWork/github/qq-music-api/.worktrees/api-explorer/docs/superpowers/specs/2026-05-01-api-explorer-full-route-metadata-design.md)，用于将 `API Explorer` 从“少量精选接口”扩展为“覆盖 `router.ts` 全部已挂载路由”的实现工作拆解为可执行、可验证的阶段任务。

本计划的核心目标如下：

1. 让 `src/routes/router.ts` 中全部路由都进入 Explorer。
2. 保留当前高频接口的精细元数据体验。
3. 为普通接口提供最小可用元数据，避免页面中出现“有路由但不可见”的缺口。
4. 通过测试把“全量覆盖”固定为后续回归门禁。

## 2. 实施原则

- 先覆盖，再精修：优先保证全部路由可见，再针对重点接口补细节。
- 先自动生成，再手工覆盖：减少重复劳动，保留精细控制点。
- 先兼容现有页面，再考虑后续优化：不重写 Explorer 前端协议。
- 先建立回归测试，再继续扩展：避免后续新增路由时再次漏配。
- 仅修改与 Explorer 扩展直接相关的文件：保持改动聚焦。

## 3. 交付范围

本次实施计划覆盖以下交付物：

- 更新后的 `src/config/apiExplorer.ts`
- 必要的元数据生成辅助函数
- 对应单元测试和覆盖测试
- 更新后的 `/explorer/metadata`
- 完成后的 Explorer 页面验证结果

本计划不覆盖：

- OpenAPI / Swagger 标准文档生成
- 全部 query/body 自动推断
- Explorer 页面的大规模 UI 重构

## 4. 里程碑概览

### 里程碑 M1：建立全量基础路由清单

目标：

- 把 `router.ts` 中全部已挂载路由映射为基础元数据来源

完成标准：

- 已挂载路由都有对应的基础描述项

### 里程碑 M2：完成元数据自动生成逻辑

完成标准：

### 里程碑 M3：保留高频接口的精细覆盖能力

目标：

- 当前已存在的高价值接口继续保留默认值、query 参数、body 示例

完成标准：

- 现有精选接口体验不回退

### 里程碑 M4：完成覆盖测试与回归

目标：

- 为“全部路由都被 Explorer 收录”建立自动化测试

完成标准：

- `lint`、`test`、功能验证全部通过

## 5. 分阶段实施步骤

## 阶段 1：整理基础路由数据源

### 目标

建立一份与 `router.ts` 对齐的全量基础路由清单。

### 执行动作

1. 逐条梳理 `src/routes/router.ts` 中已挂载路由。
2. 为每条路由建立基础条目：
   - `method`
   - `path`
   - `name`
   - `category`
3. 对分类做统一收敛，避免命名漂移。
4. 明确哪些接口属于手工精修保留项。

### 产出

- 全量基础路由清单
- 稳定的分类约定

### 完成标准

- `router.ts` 中不存在“已挂载但无基础条目”的路由

## 阶段 2：实现最小元数据自动生成

### 目标

从基础路由清单生成 Explorer 可以直接消费的最小元数据。

### 执行动作

1. 在 `src/config/apiExplorer.ts` 中引入生成逻辑。
2. 为每条基础路由生成：
   - `id`
   - `name`
   - `category`
   - `description`
   - `method`
   - `path`
   - `pathParams`
3. 实现路径参数提取函数：
   - 识别 `:param`
   - 识别 `:param?`
   - 标记 `required`
4. 保证生成逻辑输出结构与当前 Explorer 页面兼容。

### 产出

- 元数据生成辅助函数
- 可自动生成的最小元数据

### 完成标准

- 低频接口无需手工大对象也能出现在 Explorer 中

## 阶段 3：合并手工覆盖配置

### 目标

在“全量自动生成”的基础上保留高频接口的体验质量。

### 执行动作

1. 把当前已存在的高频接口定义迁移为覆盖配置层。
2. 合并规则遵循：
   - 默认生成最小元数据
   - 手工覆盖同名字段
3. 对以下类型接口优先保留精修：
   - 搜索类
   - 歌词类
   - 专辑类
   - 批量 `POST` 类
4. 检查扩展后页面中的默认示例和参数提示是否仍然可用。

### 产出

- 精修覆盖配置层
- 最终合并后的 Explorer 元数据

### 完成标准

- 精选接口体验不回退
- 全量接口列表显著扩展

## 阶段 4：补测试与防回归断言

### 目标

建立对全量路由覆盖的自动化保护。

### 执行动作

1. 新增测试验证：
   - 全部已挂载路由均被 Explorer 收录
   - 自动提取的 `pathParams` 正确
   - 手工覆盖配置优先生效
2. 复用现有 `/explorer/metadata` 路由测试，补强断言。
3. 为关键生成函数补边界测试：
   - 多个可选参数
   - 无参数接口
   - `POST` 接口

### 产出

- 路由覆盖测试
- 元数据生成测试
- 覆盖配置优先级测试

### 完成标准

- 新增路由若未进入 Explorer，会直接触发测试失败

## 阶段 5：回归验证与页面测试

### 目标

确认扩展后的 Explorer 页面在真实服务下仍然可用。

### 执行动作

1. 运行静态检查：
   - `npm run lint`
2. 运行测试：
   - `npm test`
3. 启动本地服务并验证：
   - `/explorer`
   - `/explorer/metadata`
4. 在页面中抽查不同类型接口：
   - 无参数接口
   - 多路径参数接口
   - `POST` 接口
5. 确认页面可以正常渲染新增的大量接口列表。

### 产出

- 完整验证结果
- 可访问的本地 Explorer 预览地址

### 完成标准

- Explorer 页面可正常加载并展示全部路由元数据

## 6. 任务拆解清单

11. 跑 `lint`、`test`
12. 启动 Explorer 页面进行功能验证

## 7. 文件级实施清单

预计主要改动文件如下：

- `src/config/apiExplorer.ts`

- `tests/apiExplorer.util.test.ts`
- `tests/explorer.routes.test.ts`

## 8. 测试计划

### 单元测试

重点验证：

- 路由到元数据的映射正确性
- `pathParams` 提取正确性
- `id` 和 `name` 的稳定生成
- 覆盖配置优先级

### 集成测试

重点验证：

- `/explorer/metadata` 返回结构完整
- 返回接口条目数与路由清单一致或更高

### 功能测试

手工验证以下流程：

1. 启动服务
2. 打开 `/explorer`
3. 确认接口下拉框包含全部路由
4. 抽查 `GET` 接口
5. 抽查多参数接口
6. 抽查 `POST` 接口

### 覆盖率策略

- 优先增加纯逻辑测试，保证新增代码覆盖率高
- 不通过脆弱 DOM 断言堆覆盖率
- 重点覆盖自动生成和映射逻辑

## 9. 风险与回退策略

### 风险 1：全量元数据导致配置文件过长

回退方案：

- 继续把基础路由清单和覆盖配置拆成独立常量
- 必要时拆分为多个模块文件

### 风险 2：分类规则不稳定

回退方案：

- 固定分类枚举
- 先使用稳定分组，不做过度细化

### 风险 3：页面一次性展示太多接口影响可读性

回退方案：

- 保持现有结构先完成功能
- 若必要，再追加轻量搜索或分类筛选优化

### 风险 4：部分接口仅靠路径参数不足以可测

回退方案：

- 保留最小可用接入
- 后续再增补 query/body 精修配置
