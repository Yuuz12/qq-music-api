# 发布前审查与修复 Spec

## 1. 文档目标

本 Spec 定义 `qq-music-api` 在当前代码库范围内的发布前审查与修复方案，采用“分层审查 + 分批修复”的执行方式，目标是在不做无关重构的前提下，将仓库提升到可验证、可启动、可构建、可交付的状态。

本文档同时包含设计说明与实施计划，作为后续修复工作的统一依据。

## 2. 背景与上下文

当前仓库为基于 `Koa + TypeScript + Jest + Biome` 的 QQ 音乐接口服务，具备如下可见基础：

- 应用入口为 `src/app.ts`，默认通过 `npm start` 以 `ts-node` 方式启动。
- 静态检查工具为 `Biome`，当前脚本为 `npm run lint`。
- 单元测试框架为 `Jest + ts-jest`，当前脚本为 `npm test`。
- 测试已配置覆盖率采集，但全局阈值当前仅为 `branches/functions 50`、`lines/statements 75`。
- Docker 部署入口为仓库根目录 `Dockerfile`，容器启动命令为 `npm start`。

用户额外明确的交付要求：

- 以仓库内可验证项为边界进行全面检查和修复。
- 必须支持本地启动。
- 必须支持 Docker 构建与部署，且镜像配置可正常工作。

## 3. 目标

本次工作的目标如下：

1. 识别并修复当前仓库中可通过静态分析、测试执行、启动验证、构建验证发现的高优先级问题。
2. 验证并修复关键运行链路，包括配置加载、HTTP 服务启动、路由挂载、请求工具与核心控制器/服务的数据传递链路。
3. 运行并修复现有单元测试，使测试集尽可能全量通过。
4. 补充必要测试，使覆盖率达到不低于 90% 的目标；若短期内无法达到，则明确记录当前差距、原因与补齐策略。
5. 验证 `npm start` 与 Docker 运行链路可用，确保仓库具备本地与容器化运行能力。
6. 给出最终验收结果，包括静态检查、单元测试、功能验证与部署验证结论。

## 4. 非目标

以下内容不在本次工作的直接承诺范围内：

- 真实生产环境 24 小时连续运行证明。
- 外部云平台、CI/CD 平台、制品仓库、Kubernetes 等实际部署环境联调。
- 依赖 QQ 音乐线上接口稳定性的长期 SLA 评估。
- 大规模架构重构、接口协议重设计、与当前问题无直接关系的代码清理。
- 无现成基建前提下的完整端到端浏览器自动化测试平台搭建。

对于上述事项，如发现明显缺口，将在最终报告中标记为“后续建设项”。

## 5. 现状基线判断

基于当前代码结构，初步判断存在以下高风险点，需要进入正式审查：

### 5.1 启动与运行时风险

- `src/app.ts` 在模块初始化阶段执行外部命令 `npm info qq-music-api version`，可能导致启动时额外阻塞、失败噪声或离线环境异常。
- 应用启动时存在多处直接 `console.log` 与配置提示输出，但缺少统一错误边界与启动失败分类。
- `ConfigManager` 在配置校验失败时直接 `process.exit(1)`，对测试与复用场景不友好，需要确认是否存在更好的错误传播策略。

### 5.2 请求与资源管理风险

- `src/util/request.ts` 基于全局 `axios.defaults` 配置请求，需检查超时、响应类型、错误传播、日志输出和可测试性是否充分。
- 需确认服务层调用是否存在未捕获异常、未校验响应结构、边界值处理不一致等问题。

### 5.3 测试与覆盖率风险

- 仓库已有较多测试文件，但 `README` 中历史说明与当前实际状态不一致，说明文档与代码存在偏差。
- 当前 Jest 覆盖率阈值低于本次交付目标，需要通过“修复 + 补测”提升。
- 需要确认是否存在只覆盖成功路径、缺少异常路径和边界条件的情况。

### 5.4 构建与部署风险

- `Dockerfile` 当前使用 `npm install --production`，但运行命令依赖 `ts-node` 与 TypeScript 源码启动，需要核对这些运行时依赖是否在生产安装范围内有效。
- 仓库未见显式编译脚本，说明部署方式依赖运行时转译，需确认镜像体积、启动一致性和环境兼容性。

## 6. 设计原则

本次审查与修复遵循以下原则：

- 先证据后修改：所有结论以 `lint`、`test`、启动日志、构建结果和代码路径为依据。
- 先高风险后低风险：优先处理会导致启动失败、测试失败、错误响应、Docker 不可用的问题。
- 最小必要修改：只修复影响发布质量的缺陷，不做与目标无关的大规模重构。
- 分层准入：每一阶段完成后才进入下一阶段，避免问题扩散。
- 可回归验证：每项修复都要有对应的验证手段，优先通过自动化测试固定行为。

## 7. 推荐方案

采用 `方案 B：分层审查 + 分批修复`。

### 7.1 方案说明

将全量工作拆分为六个阶段：

1. 基线采集
2. 静态质量审查
3. 运行与数据流审查
4. 测试与覆盖率修复
5. 本地启动与 Docker 验证
6. 结果复核与发布结论

### 7.2 选择原因

- 相比一次性全量修复，该方案更容易定位问题来源。
- 相比先补大量基建，该方案能优先交付发布可用性相关结果。
- 适合当前仓库已有测试和 Docker 文件、但质量门禁尚未完全收敛的状态。

## 8. 执行阶段设计

### 阶段 1：基线采集

目标：

- 记录当前脚本、测试、配置、Docker、目录结构的真实状态。
- 形成本次修复前的基线证据。

执行项：

- 检查 `package.json`、`jest.config.js`、`biome.json`、`Dockerfile`、`tsconfig.json`。
- 统计测试分布和覆盖范围。
- 识别启动路径、配置入口、请求封装与主要路由入口。

准出标准：

- 形成问题清单初稿。
- 明确后续优先级排序。

### 阶段 2：静态质量审查

目标：

- 找出语法、风格、可疑用法和潜在错误传播问题。

执行项：

- 运行 `npm run lint`。
- 获取 TypeScript 诊断信息。
- 审查异常处理、空值处理、动态参数读取、日志输出和高风险全局副作用。

重点关注：

- 未处理 Promise 拒绝。
- 启动时副作用过重。
- 配置读取失败时的退出逻辑。
- `any`、类型断言掩盖真实问题、无意义日志或错误日志丢失上下文。

准出标准：

- 所有可修复静态问题均已修复。
- 最近修改文件的诊断信息为零或仅保留已记录的非阻塞项。

### 阶段 3：运行与数据流审查

目标：

- 验证请求从路由到控制器、服务、工具函数的传递链路是否一致。

执行项：

- 抽查关键接口：搜索、歌曲信息、歌词、歌单、排行榜、Cookie 配置相关流程。
- 检查参数默认值、空参数、非法参数、接口失败时的响应行为。
- 验证配置管理与请求工具之间的数据传递是否稳定。

重点关注：

- 路由可选参数未正确兜底。
- 控制器未校验输入即下发服务层。
- 服务层默认值和测试预期不一致。
- 配置对象在运行时被意外修改。

准出标准：

- 关键链路具备明确的成功与失败路径。
- 至少对高风险控制器/工具层补充单元测试或集成测试。

### 阶段 4：测试与覆盖率修复

目标：

- 使测试集全量通过，并提升覆盖率到目标水平。

执行项：

- 运行 `npm test -- --coverage`。
- 修复失效测试、过时断言和被真实代码变更打破的假设。
- 针对以下场景补测：
  - 正例
  - 反例
  - 边界条件
  - 异常处理路径

覆盖率策略：

- 优先补充 `src/app.ts` 相关运行逻辑的可测部分。
- 优先覆盖 `src/config/*`、`src/util/request.ts`、关键控制器和服务层分支。
- 若存在强外部依赖，使用 mock 固定行为，避免测试依赖真实上游网络。

准出标准：

- 测试 100% 通过。
- 覆盖率达到 `>= 90%`；若暂未达到，则必须形成明确缺口说明与后续补充任务，不得默默忽略。

### 阶段 5：本地启动与 Docker 验证

目标：

- 证明仓库在本机和容器环境都可以启动。

执行项：

- 使用 `npm start` 验证应用启动。
- 必要时用 `NODE_ENV=test` 或 mock 配置隔离测试与运行环境。
- 执行 `docker build`，验证镜像构建成功。
- 执行 `docker run`，验证容器能监听预期端口并返回基础可用结果。

重点关注：

- 容器内依赖完整性。
- 启动命令是否依赖未安装的开发依赖。
- 配置文件路径、静态资源路径、端口暴露和工作目录一致性。

准出标准：

- 本地启动成功。
- Docker 镜像构建成功。
- 容器启动成功且至少一个基础路由可访问。

### 阶段 6：结果复核与发布结论

目标：

- 输出最终可发布性结论和残余风险清单。

执行项：

- 复跑 `lint`、`test`、覆盖率、本地启动、Docker 验证。
- 汇总修改内容、验证命令、结果、覆盖率数据和未解决项。
- 给出“可发布 / 条件可发布 / 不可发布”的结论。

准出标准：

- 所有证据可复现。
- 结论与证据一致，无口头承诺替代验证。

## 9. 验证矩阵

| 维度 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 代码风格与可疑问题 | `npm run lint` | 无错误 |
| 类型与编辑器诊断 | TypeScript / IDE diagnostics | 无新增阻塞问题 |
| 单元测试 | `npm test` | 全量通过 |
| 覆盖率 | Jest coverage | `>= 90%` |
| 本地启动 | `npm start` | 服务正常监听并输出可用日志 |
| 路由基础可用性 | `supertest` 或本地请求验证 | 核心路由至少覆盖健康链路 |
| Docker 构建 | `docker build` | 成功产出镜像 |
| Docker 运行 | `docker run` | 容器正常启动并可访问 |

## 10. 问题分级与处理策略

### P0

阻塞发布的问题，例如：

- 启动失败
- Docker 构建失败
- 测试大面积失败
- 关键接口参数处理错误导致异常响应

处理策略：必须在本轮修复闭环内解决。

### P1

高风险但不一定立刻阻塞的问题，例如：

- 异常处理缺失
- 覆盖率缺口集中在高频核心模块
- 配置与运行环境耦合过重

处理策略：原则上本轮解决；若未解决，必须给出可接受的临时结论与明确后续计划。

### P2

中低风险问题，例如：

- 文档与实现不一致
- 局部风格问题
- 非关键模块的轻微重复或可维护性问题

处理策略：在不影响主线进度时顺手修复，否则列入后续清单。

## 11. 具体实施计划

### 11.1 任务拆分

任务 1：建立基线

- 运行并记录 `lint`、`test`、覆盖率、`npm start`、`docker build` 的首次结果。
- 收集失败日志，按 P0/P1/P2 分类。

任务 2：修复静态与启动问题

- 优先修复会导致 lint 失败、类型诊断报错、启动报错的问题。
- 对 `src/app.ts`、`src/config/manager.ts`、`src/util/request.ts` 等高风险文件做定向处理。

任务 3：修复测试并补充测试

- 修复现有失败测试。
- 为高风险模块补正例、反例、边界和异常路径测试。
- 必要时调高 Jest 覆盖率阈值，使门禁与目标一致。

任务 4：验证关键功能链路

- 基于已有控制器测试与 `supertest` 补充集成验证。
- 抽样验证 Cookie 配置、搜索、歌词、歌曲信息、歌单等关键路由。

任务 5：修复 Docker 与部署链路

- 验证 Dockerfile 是否与当前运行模式匹配。
- 修复镜像安装策略、启动命令或缺失依赖。

任务 6：最终复核与交付

- 全量复跑所有验证项。
- 汇总结果并输出最终交付结论。

### 11.2 执行顺序

推荐严格按以下顺序推进：

1. `lint / diagnostics`
2. `test / coverage`
3. `启动链路`
4. `Docker 链路`
5. `文档与结果整理`

原因：

- 静态问题最容易提前暴露结构性缺陷。
- 测试失败可帮助快速识别行为回归。
- 启动与 Docker 放在修复后验证，可以减少重复等待成本。

## 12. 风险与应对

### 风险 1：测试依赖外部网络或线上接口状态

应对：

- 优先使用 mock 或固定响应样本。
- 将真实网络依赖从单元测试中隔离出去。

### 风险 2：配置初始化副作用影响测试稳定性

应对：

- 拆分可测试逻辑与启动副作用。
- 必要时通过环境变量或依赖注入避免测试时真实退出进程或执行外部命令。

### 风险 3：Docker 运行依赖开发时工具

应对：

- 明确运行时依赖与开发依赖边界。
- 若继续使用 `ts-node` 运行源码，则必须保证镜像内包含必需依赖；若不合理，则补充构建产物与启动脚本。

## 13. 完成定义

本 Spec 对应工作的完成定义如下：

- `linter_result`: pass
- `unit_test_result`: pass
- `func_test_result`: pass
- `status`: 仅当以上结论全部成立且 Docker 验证通过时，输出成功

其中：

- `func_test_result` 指仓库内可验证的功能链路验证结果，不包含真实生产环境长期稳定性证明。
- 若某项由于仓库现状无法达到目标，必须在最终报告中明确说明差距，不允许以模糊措辞替代结论。
