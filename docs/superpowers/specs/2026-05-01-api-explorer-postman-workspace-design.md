# API Explorer 侧栏整合与 Postman 风格工作区 Spec

## 1. 文档目标

本 Spec 定义 `.worktrees/api-explorer` 中 API Explorer 页面在现有“左侧目录 + 右侧工作台”基础上的二次重构方案。

本轮重构目标不是推翻已有工作台，而是在当前版本上进一步优化两个核心问题：

1. 左侧目录结构仍然偏分散，`sidebar-header`、导航链接、筛选区和接口列表之间的层级关系不够紧凑。
2. 右侧工作区虽然功能完整，但“参数输入 / 请求预览 / 响应结果 / 请求日志”仍然偏静态卡片化，不够接近高频调试工具的操作节奏。

本次设计目标是把 Explorer 调整为更接近 Postman 的信息组织方式，同时保持当前原生 JS 架构、后端元数据协议和请求链路不变。

## 2. 背景与现状

当前 Explorer 已经具备以下能力：

- 左侧支持接口搜索、方法过滤和接口列表切换。
- 右侧支持接口概览、参数输入、请求预览、响应展示和请求日志。
- 请求日志已支持会话内记录与详情查看。
- 首页入口已统一指向 `/explorer`。

当前页面的主要问题如下：

- 左侧 `sidebar-header` 和 `sidebar-links` 是两个独立块，视觉上割裂。
- 筛选区和接口列表被拆成两个 panel，导致“筛选 -> 浏览 -> 切换接口”的工作流被打断。
- 右侧请求配置被拆成“参数输入”和“请求预览”两个独立 panel，信息路径过长。
- 响应结果和请求日志都是普通卡片，缺少“高频展开、低频折叠”的调试节奏控制。

## 3. 目标

本次工作的目标如下：

1. 将左侧 `sidebar-header` 与 `sidebar-links` 整合为单一顶部 `header`。
2. 将接口搜索、方法过滤、统计摘要和接口列表整合到同一个侧栏工作区中。
3. 保证左侧只有接口列表区域滚动，顶部说明和筛选区固定可见。
4. 将右侧改造成同层级的 Postman 风格工作区。
5. 将“参数输入”和“请求预览”合并为统一的 `请求配置` 面板。
6. 让 `当前接口概览`、`请求配置`、`响应结果`、`请求日志` 支持独立展开与折叠。
7. 不使用抽屉、浮层或层级跳转，全部交互都在同一页面层级完成。

## 4. 非目标

以下事项不在本次工作范围内：

- 修改 `/explorer/metadata` 的数据协议。
- 引入 React、Vue 或其他前端框架。
- 引入抽屉式历史面板、悬浮控制台或多标签请求页。
- 做本地持久化面板状态或跨会话恢复。
- 修改服务端请求逻辑与控制器实现。

## 5. 方案选型

本次采用 `方案 A：单一侧栏 + 同层级折叠工作区`。

### 5.1 方案 A：单一侧栏 + 同层级折叠工作区

- 左侧统一为“顶部头区 + 下方筛选与接口列表工作区”。
- 右侧统一为单列折叠工作区。
- 请求配置内部合并参数输入、Body JSON 和请求摘要。

优点：

- 最符合用户当前的布局诉求。
- 信息路径短，适合高频切换接口与重复调试。
- 保持同层级，认知负担小。
- 展开/折叠比标签切换更利于同时对照请求、响应和日志。

缺点：

- 需要改造 HTML 结构、面板状态管理和部分 CSS 布局。

### 5.2 备选方案 B：双列卡片 + 局部折叠

- 左侧结构微调，右侧保留双列卡片，只增加折叠。

优点：

- 改动较小。

缺点：

- 仍然不是最优的阅读顺序。
- 请求配置与响应结果之间的关系不够直接。

### 5.3 备选方案 C：标签切换式工作区

- 右侧改成请求、响应、日志的标签页。

优点：

- 屏幕利用率高。

缺点：

- 切换成本高。
- 不利于同时对照请求参数、响应和历史日志。

### 5.4 选择原因

选择方案 A 的原因如下：

- 用户明确要求所有区域在同一个层级上，不要抽屉。
- 用户希望“最大程度获取信息”，折叠面板比标签页更利于同时保留上下文。
- 请求预览与参数输入天然属于同一个“请求配置”过程，合并后更接近 Postman 的组织方式。

## 6. 页面信息架构

### 6.1 左侧结构

左侧侧栏分为两个层级：

1. `sidebar-top`
2. `sidebar-body`

#### `sidebar-top`

顶部头区整合以下内容：

- 产品标识
- 页面标题
- 页面描述
- 返回首页链接
- 在线文档链接

`sidebar-top` 替代当前分离的 `sidebar-header` 与 `sidebar-links`。

#### `sidebar-body`

侧栏工作区按顺序包含：

- 搜索框
- 方法过滤器
- 结果统计摘要
- 当前激活接口提示
- 接口列表
- 空状态提示

其中：

- 顶部筛选和摘要区域固定显示。
- 只有接口列表区域滚动。
- 搜索和过滤操作始终和结果列表属于同一个视觉工作区。

### 6.2 右侧结构

右侧工作区统一为单列 `panel stack`，按固定顺序包含四个主面板：

1. `overview`
2. `request`
3. `response`
4. `logs`

每个主面板都处于同层级，不使用覆盖式交互。

## 7. 左侧交互设计

### 7.1 侧栏滚动规则

左侧侧栏本身固定在视口内，不整体滚动。

滚动行为规则如下：

- `sidebar-top` 不滚动。
- `sidebar-body` 作为容器承载筛选和列表。
- 其中只有 `endpoint-list` 区域滚动。

这样可以保证：

- 搜索框始终可见。
- 方法过滤器始终可见。
- 用户滚动长列表时，不需要反复回到顶部调整筛选条件。

### 7.2 搜索与过滤规则

沿用当前搜索和方法过滤规则：

- 搜索匹配 `name`、`category`、`path`
- 方法过滤支持 `All`、`GET`、`POST`
- 无结果时左侧显示空状态，右侧不清空

本次新增的只是布局组织变化，不改变筛选逻辑。

### 7.3 接口选择规则

点击接口项后：

- 当前激活接口立即高亮切换
- 右侧概览和请求配置立即刷新
- 已有折叠状态不被重置

## 8. 右侧工作区设计

### 8.1 概览面板

`overview` 面板用于快速确认当前接口上下文，展示：

- 接口名称
- 描述
- 分类
- 方法
- 路径

该面板默认展开，但内容相对轻量。

### 8.2 请求配置面板

`request` 面板是本次重构的核心，合并以下内容：

- 路径参数
- 查询参数
- Body JSON
- 请求摘要
- 发送请求按钮

设计原则：

- “参数输入”和“请求预览”不再拆成两个 panel。
- 请求摘要作为请求配置的一部分，始终紧邻输入内容。
- 用户修改参数时，可以立刻看到最终请求方法、URL 和请求体。

### 8.3 响应结果面板

`response` 面板展示最近一次请求的结果，包含：

- 状态码
- 耗时
- 响应正文

交互规则：

- 默认展开
- 请求成功或失败后都更新内容
- 如果该面板被折叠，首次请求完成后允许自动展开一次，保证结果不被隐藏

### 8.4 请求日志面板

`logs` 面板展示当前会话中的历史请求，包含：

- 日志列表
- 当前选中日志的详情

交互规则：

- 日志新增时不强制展开该面板
- 面板关闭时仍然继续记录日志
- 用户打开后可以回看会话历史

## 9. 展开与折叠设计

### 9.1 主面板折叠状态

新增主面板状态：

```js
panelState = {
  overview: true,
  request: true,
  response: true,
  logs: true,
}
```

规则如下：

- 四个主面板默认全部展开
- 用户可以单独折叠或展开任意一个面板
- 切换接口时保留当前折叠状态
- 折叠状态仅保存在当前页面内存中

### 9.2 请求配置子区块折叠状态

请求配置面板内部新增子区块折叠状态：

```js
requestSectionState = {
  pathParams: true,
  queryParams: true,
  body: true,
  preview: true,
}
```

规则如下：

- 有内容的区块默认展开
- 无内容的区块直接隐藏，而不是展示空壳
- 用户可以单独折叠 `路径参数`、`查询参数`、`Body JSON`、`请求摘要`

### 9.3 折叠交互样式

折叠控件统一放在面板头部右侧，使用：

- 状态箭头
- 展开/收起按钮

交互要求：

- 点击按钮可以切换状态
- 点击面板头部空白区也可切换
- 使用短时高度过渡和箭头旋转反馈
- 不使用抽屉、遮罩或浮层

## 10. 状态模型设计

在现有状态基础上，新增以下字段：

- `panelState`
- `requestSectionState`

保留以下原有字段：

- `metadata`
- `endpointMap`
- `activeEndpointId`
- `searchKeyword`
- `methodFilter`
- `visibleEndpointIds`
- `requestLogs`
- `selectedLogId`

状态设计原则：

- 折叠状态独立于接口选择状态
- 筛选状态独立于请求日志状态
- 发送请求只更新响应和日志，不重置折叠状态

## 11. HTML 结构设计

`public/explorer/index.html` 重构后应满足以下目标：

- 左侧以 `aside.sidebar` 作为整体容器
- 左侧内部包含：
  - `header.sidebar-top`
  - `section.sidebar-body`
- `sidebar-body` 内部包含稳定锚点：
  - 搜索输入
  - 方法过滤
  - 统计摘要
  - 当前接口提示
  - 接口空状态
  - 接口列表
- 右侧 `main.workspace` 内部包含四个主 panel：
  - `panel-overview`
  - `panel-request`
  - `panel-response`
  - `panel-logs`

新增的稳定 DOM 锚点至少包括：

- 主面板折叠按钮
- 请求配置子区块折叠按钮
- 请求摘要内嵌容器
- 日志列表容器
- 日志详情容器

## 12. 前端代码结构设计

`public/explorer/app.js` 在现有基础上继续按职责细化，新增如下 helper 分组：

- `panel helpers`
  - `togglePanel(panelKey)`
  - `renderPanelState()`
- `request section helpers`
  - `toggleRequestSection(sectionKey)`
  - `renderRequestSectionState()`
- `request config helpers`
  - `renderRequestConfig(endpoint)`
  - `renderInlineRequestPreview(endpoint)`
- `sidebar helpers`
  - 渲染固定筛选区
  - 渲染接口列表滚动区

保留并复用当前逻辑：

- 搜索和过滤计算
- URL 构造
- 参数校验
- 请求发送
- 日志创建与更新

### 12.1 不建议的实现方式

本次不建议：

- 通过大量 `innerHTML` 字符串拼接整个工作区
- 在多个地方散落维护折叠类名
- 用一组互相覆盖的布尔变量替代结构化状态对象

## 13. 样式设计边界

本轮样式重点如下：

- 强化左侧头区与工作区的分层关系
- 强化右侧主面板的工具化气质
- 收紧面板间距，提高信息密度
- 让日志列表和响应区更接近调试工具风格

具体样式约束：

- 仍采用简洁白底卡片体系
- 不引入复杂装饰、渐变边框或拟物效果
- 面板头部保持统一高度和对齐
- 折叠动画保持克制，不做长时间运动

## 14. 错误处理与边界条件

### 14.1 无参数区块

当某个请求配置子区块无内容时：

- 直接隐藏对应区块
- 不显示“暂无内容”的占位区域

### 14.2 面板折叠时的请求行为

如果用户在 `request` 面板展开状态下发起请求，然后折叠：

- 请求继续正常执行
- 响应完成后不影响日志记录
- `response` 面板若被折叠，可自动展开一次以展示最新结果

### 14.3 左侧无匹配结果

当左侧搜索或过滤后无结果时：

- 左侧显示空状态
- 右侧保持上一次激活接口
- 已有折叠状态不变

## 15. 测试设计

### 15.1 单元测试

新增或扩展前端纯逻辑测试，重点覆盖：

- 主面板折叠状态切换
- 请求配置子区块折叠状态切换
- 搜索和过滤在新布局下仍返回正确结果
- 请求日志在面板折叠时仍可正常更新

### 15.2 功能验证

手工验证至少覆盖以下场景：

1. 左侧头区已合并，导航和标题处于同一 header
2. 左侧筛选区和接口列表处于同一个工作区
3. 左侧长列表仅列表区域滚动
4. 请求配置面板中同时展示参数输入和请求摘要
5. 四个主面板都可以独立展开/折叠
6. 请求配置内的子区块可以独立展开/折叠
7. 响应结果和请求日志仍可正常更新

### 15.3 发布门禁

需满足以下结果：

- `npm run lint`
- `npm test`
- 必要的手工功能验证

并确保最终结果满足：

- `linter_result`: pass
- `unit_test_result`: pass
- `func_test_result`: pass
- `status`: 成功

## 17. 风险与应对

### 风险 1：折叠状态与接口切换相互干扰

应对：

- 单独维护 `panelState` 与 `requestSectionState`
- 明确切换接口不重置折叠状态

### 风险 2：请求配置面板过长

应对：

- 使用子区块折叠降低视觉压力
- 仅显示有内容的参数区块

### 风险 3：左侧整合后滚动行为混乱

应对：

- 明确只有 `endpoint-list` 滚动
- 不让整个侧栏或整个筛选区一起滚

## 18. 与前一版 Spec 的关系

本 Spec 是对 `2026-05-01-api-explorer-layout-refactor-design.md` 的增量升级，具体关系如下：

- 保留原有“左侧目录 + 右侧工作台”的总体方向
- 调整左侧目录内部层级组织
- 将右侧从静态卡片进一步升级为折叠式工作区
- 将原来的“请求预览独立 panel”收敛为“请求配置内部摘要区”

若后续实现发生冲突，应以本 Spec 对页面结构与交互规则的更新为准。
