# 接口日志补齐与测试增强 Spec

## 1. 文档目标

本 Spec 定义 `qq-music-api` 当前仓库内“为每个接口补充日志输出，并补充单元测试”的设计方案与实施边界。

目标不是简单增加日志行数，而是让每个 HTTP 接口都具备可追踪、可定位、可回归验证的最小可用观测能力，并通过自动化测试固定关键日志行为，保证改动达到可发布状态。

## 2. 背景与上下文

当前仓库具备以下基础：

- 路由入口集中在 `src/routes/router.ts`。
- HTTP 接口主要由 `src/controllers/*` 承载，当前可见为 `31` 个异步控制器文件。
- 另有 `cookies.ts` 暴露 `getCookie` 与 `setCookie` 两个接口处理函数。
- 服务层位于 `src/services/*`，部分模块已经存在零散 `logger.error(...)` 异常日志。
- 仓库已提供较完整的控制器测试与部分服务层测试，测试框架为 `Jest + ts-jest`。
- 统一日志出口为 `src/util/logger.ts`，且测试环境默认仅输出 `error` 级别日志以减少噪音。

当前主要问题：

- 绝大多数控制器未记录请求进入、参数缺失、成功返回和未捕获异常等关键节点。
- 服务层日志分布不均匀，很多模块只有异常日志，缺少对关键追踪点的上下文信息。
- 现有测试主要验证功能返回，较少验证日志行为，导致后续重构时容易丢失追踪能力。

## 3. 目标

本次工作的目标如下：

1. 为每个 HTTP 接口补齐统一风格的控制器层日志。
2. 为核心服务链路补齐必要的服务层关键日志，满足问题追溯与错误定位需求。
3. 在不泄漏敏感信息、不输出超大响应体的前提下，统一日志字段与摘要规则。
4. 补充自动化测试，覆盖公共日志模式、重点接口日志断言和服务层异常日志断言。
5. 保证 `npm run lint`、`npm test` 和功能验证通过，满足发布前质量门禁。

## 4. 非目标

以下事项不在本次工作直接承诺范围内：

- 引入新的第三方日志框架、日志平台或链路追踪系统。
- 重写全部控制器为统一基类、装饰器或中间件体系。
- 将所有服务层函数都改造成细粒度全埋点流水日志。
- 记录完整上游响应包、Cookie 原文或其他潜在敏感数据。
- 搭建新的端到端日志采集基础设施。

## 5. 范围定义

### 5.1 接口范围

本次覆盖 `src/routes/router.ts` 已挂载的全部 HTTP 路由，包括：

- 搜索类接口：`getHotkey`、`getSearchByKey`、`getSmartbox`
- 歌单类接口：`getSongListCategories`、`getSongLists`、`batchGetSongLists`、`getSongListDetail`
- 歌曲类接口：`getSongInfo`、`batchGetSongInfo`、`getLyric`、`getMusicPlay`、`getDownloadQQMusic`
- 歌手类接口：`getSingerList`、`getSimilarSinger`、`getSingerAlbum`、`getSingerHotsong`、`getSingerMv`、`getSingerDesc`、`getSingerStarNum`
- MV、专辑、评论、推荐、榜单、票务、图片等其他接口
- Cookie 相关接口：`/user/getCookie`、`/user/setCookie`

### 5.2 服务范围

服务层不是“全量深埋点”，而是“关键追踪点补齐”。重点覆盖：

- 已存在日志但信息不足的服务模块
- 直接访问 QQ 音乐上游接口的服务模块
- 带有格式化、解析或条件分支的服务模块
- 与用户明确点名的核心定位链路相关的模块

## 6. 设计原则

本次设计遵循以下原则：

- 统一出口：全部日志继续使用 `src/util/logger.ts`。
- 结构一致：控制器与服务层日志命名和字段尽量统一，便于检索。
- 摘要优先：日志记录关键参数和结果摘要，不记录超大 payload。
- 敏感最小化：Cookie、请求头、上游返回体只记录必要信息或脱敏摘要。
- 测试可控：日志测试优先断言“模式”和“关键字段”，避免对完整文案做脆弱绑定。
- 最小侵入：不为日志而大幅重构业务逻辑，优先引入轻量 helper 降低重复代码。

## 7. 方案选型

采用 `方案 A：控制器层统一日志 + 服务层关键日志 + 公共模式测试`。

### 7.1 方案说明

该方案包含三部分：

1. 控制器层统一补齐请求生命周期日志。
2. 服务层只补关键追踪点，不做全量流水日志。
3. 测试层采用“公共模式 + 重点抽样 + 异常兜底”的组合验证。

### 7.2 选择原因

- 仅在控制器层加日志无法满足“定位到服务内部失败点”的需求。
- 对全部服务层做细粒度日志会造成改动面过大，测试和维护成本过高。
- 组合方案既能覆盖每个接口，又能在复杂链路保留足够上下文，符合当前仓库的规模与可维护性要求。

## 8. 日志设计

### 8.1 控制器层日志模型

每个接口在控制器层至少覆盖以下四类事件：

1. `request.received`
2. `request.validation_failed`
3. `request.succeeded`
4. `request.failed`

推荐字段如下：

| 字段 | 含义 |
| --- | --- |
| `scope` | 固定为 `controller` |
| `controller` | 控制器名称，如 `getAlbumInfo` |
| `route` | 路由路径或稳定标识 |
| `method` | HTTP 方法 |
| `params` | 关键参数摘要 |
| `status` | 返回状态码 |
| `durationMs` | 请求耗时，若实现成本可控则记录 |
| `result` | 结果摘要，如数据条数、是否命中、是否格式化 |
| `error` | 错误对象或错误摘要 |

### 8.2 控制器层日志触发时机

#### 请求进入

在控制器解析参数后、调用服务前记录：

- 接口名
- 关键参数摘要
- 是否命中可选分支，例如 `isFormat`、分页参数、排序参数

#### 参数校验失败

对当前已有的参数缺失分支统一记录：

- 缺失字段名
- 当前请求参数摘要
- 返回状态码 `400`

#### 成功返回

在拿到服务返回并写入 `ctx` 后记录：

- 最终状态码
- 结果摘要，而不是完整响应体
- 可选记录耗时

#### 未捕获异常

对当前控制器内部可能抛出的同步或异步异常统一捕获并记录：

- 错误对象
- 关键参数摘要
- 控制器名称

同时返回与现有风格一致的错误响应，不引入额外破坏性协议变更。

### 8.3 服务层日志模型

服务层日志只在关键追踪点记录，建议统一为以下几类事件：

1. `service.requesting`
2. `service.succeeded`
3. `service.failed`
4. `service.branch_selected`

推荐字段如下：

| 字段 | 含义 |
| --- | --- |
| `scope` | 固定为 `service` |
| `service` | 服务函数名称 |
| `upstream` | 上游接口路径或逻辑来源 |
| `params` | 发往上游的关键参数摘要 |
| `result` | 成功结果摘要 |
| `branch` | 命中分支，如 `format=true`、`order=listen` |
| `error` | 异常对象或异常摘要 |

### 8.4 服务层必补位置

以下位置定义为必补关键日志：

- 发起上游请求前
- 捕获上游异常时
- 存在显式分支选择时
- 解析、格式化、聚合结果完成后

以下位置不要求机械式打点：

- 纯参数透传且无额外分支的每一个中间变量赋值
- 明显重复、没有额外定位价值的内部步骤

### 8.5 日志摘要规则

为避免日志污染，统一采用摘要化规则：

- 分页接口只记录 `page`、`limit`、`total`、结果条数等摘要字段。
- 搜索接口只记录关键字长度、分类、页码，不记录超长响应内容。
- 歌词、评论、详情类接口只记录是否命中、是否格式化、主要标识符，不记录完整文本。
- Cookie 相关接口只记录是否存在、是否更新成功，不记录完整 Cookie 内容。
- 错误日志保留原始错误对象，同时尽量补充接口名和参数摘要。

## 9. 实现设计

### 9.1 轻量日志辅助工具

为避免在三十多个控制器中重复手写日志结构，引入一个轻量 helper 模块，职责如下：

- 生成统一字段结构
- 规范控制器层事件名称
- 生成安全的参数摘要
- 生成标准结果摘要

该 helper 不替代 `logger`，只负责把调用参数组织成一致格式，最终仍调用 `logger.info`、`logger.warn`、`logger.error`、`logger.debug`。

### 9.2 控制器改造模式

每个控制器改造为统一模式：

1. 解析并规范化参数
2. 记录 `request.received`
3. 参数缺失时记录 `request.validation_failed`
4. 调用服务
5. 写回 `ctx`
6. 记录 `request.succeeded`
7. 若抛异常，记录 `request.failed`

对 `cookies.ts` 这类一个文件包含多个接口处理函数的情况，同样按单个接口维度记录。

### 9.3 服务层改造模式

服务层按模块分两类处理：

- 已有 `catch + logger.error` 的模块：补齐请求开始、分支选择或结果摘要日志。
- 尚无日志但属于核心链路的模块：至少补 `service.requesting` 与 `service.failed`，必要时补 `service.succeeded`。

### 9.4 不采用中间件全局兜底的原因

本次不以“全局日志中间件”作为主实现方式，原因如下：

- 当前参数解析和服务调用逻辑分散在各控制器内部，中间件难以拿到稳定且有业务意义的参数摘要。
- 参数缺失与分支逻辑主要在控制器中完成，仅依靠中间件无法准确记录业务校验失败原因。
- 本次目标是“接口级定位”，控制器内显式日志更直观，也更容易补测试。

## 10. 测试设计

### 10.1 测试策略

采用“关键接口抽样 + 公共模式校验”的组合策略：

- 公共模式用于固定控制器日志事件结构
- 重点接口做显式日志断言
- 服务层重点覆盖异常分支与关键分支

### 10.2 控制器测试

控制器测试分为两层：

#### 公共模式

新增测试辅助函数，统一断言以下模式：

- 请求进入时记录 `request.received`
- 参数缺失时记录 `request.validation_failed`
- 成功路径记录 `request.succeeded`
- 异常路径记录 `request.failed`

公共 helper 只断言关键字段是否存在、事件名是否正确、控制器名是否正确，不把完整日志对象锁死。

#### 重点抽样接口

以下接口建议做完整日志断言：

- `getLyric`
- `getSearchByKey`
- `getAlbumInfo`
- `getDownloadQQMusic`
- `batchGetSongInfo`

选择理由：

- 覆盖 GET、POST、分页、可选参数、格式化分支、批量输入、外部依赖错误等多种场景。

### 10.3 服务层测试

服务层测试重点断言：

- 请求前日志是否包含关键上游路径和参数摘要
- 异常日志是否保留错误对象
- 存在分支逻辑的服务是否记录命中分支

优先复用和扩展已有测试文件，例如：

- `tests/services.get-album-info.test.ts`
- `tests/services.get-lyric.test.ts`
- `tests/services.get-search-by-key.test.ts`
- `tests/services.download-qq-music.test.ts`

### 10.4 边界与反例

本次测试必须覆盖以下类型：

- 正例：参数完整、服务返回成功
- 反例：缺失必要参数、上游请求失败
- 边界条件：空字符串、分页默认值、布尔格式化分支、空数组或无结果

### 10.5 Mock 规则

遵循当前仓库测试习惯：

- 控制器测试通过 `supertest` 验证对外行为
- 服务层测试通过 `jest.mock(...)` 隔离上游请求
- 日志通过 mock `src/util/logger.ts` 做调用断言

不依赖真实网络，不把日志测试和外部接口稳定性耦合。

## 11. 分阶段实施计划

### 阶段 1：建立日志 helper 与测试 helper

- 新增控制器/服务通用日志辅助函数
- 新增测试断言 helper
- 先在 1 至 2 个典型接口验证模式可行

### 阶段 2：批量补齐控制器日志

- 覆盖全部控制器
- 统一参数缺失与异常日志模式
- 优先保持现有响应协议不变

### 阶段 3：补齐服务层关键日志

- 优先处理已有服务测试覆盖的模块
- 再补复杂分支和上游失败高频模块

### 阶段 4：补测与回归

- 扩展控制器抽样日志测试
- 扩展服务层日志测试
- 复跑全量 lint、test、diagnostics

## 12. 风险与应对

### 风险 1：日志对象过大导致测试脆弱

应对：

- 统一使用摘要函数
- 测试只断言关键字段和事件，不锁死全部对象

### 风险 2：日志补齐引入响应协议变更

应对：

- 日志逻辑不直接修改响应结构
- 控制器异常兜底保持与现有风格一致

### 风险 3：批量改动控制器导致风格分裂

应对：

- 先建立统一 helper
- 用少量稳定字段驱动全部控制器改造

### 风险 4：测试环境日志等级导致断言缺失

应对：

- 通过 mock `logger` 断言调用，不依赖控制台真实输出
- 不把日志级别开关作为测试行为前提

## 13. 验证矩阵

| 维度 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 控制器日志覆盖 | 抽样控制器测试 + 代码检视 | 每个接口均具备统一日志入口 |
| 服务关键日志 | 服务层单测 | 核心链路具备请求/异常/关键分支日志 |
| 静态检查 | `npm run lint` | 无错误、无警告 |
| 单元测试 | `npm test` | 全量通过 |
| 覆盖率 | Jest coverage | `>= 90%` |
| 功能行为 | 现有控制器/服务测试 | 响应协议不回归 |
| 诊断检查 | IDE diagnostics | 最近修改文件无新增阻塞问题 |
