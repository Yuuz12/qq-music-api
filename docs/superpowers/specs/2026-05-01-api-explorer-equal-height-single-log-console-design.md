# API Explorer 顶部等高与单日志会话框 Spec

## 1. 文档目标

本 Spec 定义 `.worktrees/api-explorer` 中 API Explorer 右侧工作区的两个增量调整：

1. 顶部 `Request` 与 `Response` 两个 `section` 做等高对齐。
2. `Logs` 面板移除左侧独立日志列表，改为单一日志会话框展示当前会话全部请求记录。

本次调整基于现有工作区结构继续收敛，不引入新的交互模式，也不改变请求发送逻辑。

## 2. 背景与现状

当前右侧工作区存在以下问题：

- 顶部两张卡片在内容量不同时高度不一致，视觉上断层明显。
- `Logs` 面板仍保留“左侧列表 + 右侧详情”的双栏结构。
- 对当前场景来说，左侧独立日志列表增加了层级，用户需要额外理解“列表”和“详情”的分离关系。
- 当日志为空时，左侧 `div` 只保留一个空容器，缺少实际价值。

当前相关实现位于以下文件：

- `public/explorer/index.html`
- `public/explorer/app.js`
- `public/explorer/styles.css`
- `tests/explorer.routes.test.ts`

## 3. 目标

本次调整目标如下：

1. 顶部 `workspace-primary-card` 与 `workspace-response-card` 在桌面端保持同一行等高显示。
2. `Logs` 面板只保留一个日志会话框，不再保留左侧独立日志列表容器。
3. 当前会话中的所有请求日志都直接输出到日志会话框内，按时间倒序展示。
4. 长日志内容继续限制在区域内滚动，不撑开整页。
5. 保持 `Response` 面板继续展示最近一次请求结果。

## 4. 非目标

以下内容不在本次范围内：

- 修改 `/explorer/metadata` 结构。
- 增加日志搜索、筛选、折叠或多标签切换。
- 引入数据库或本地存储做日志持久化。
- 修改请求日志生成字段定义。
- 调整左侧接口列表和请求区布局。

## 5. 方案选型

本次采用 `方案 B：结构收敛 + 样式对齐`。

### 5.1 推荐方案：结构收敛 + 样式对齐

- 在顶部网格容器中让左右两张卡片自动拉伸等高。
- `Logs` 面板删除左侧 `request-log-list` 容器。
- `app.js` 中取消“选中某一条日志再展示详情”的模式，改为把全部会话日志拼接到一个 `pre` 中展示。

优点：

- 最符合当前视觉反馈。
- DOM 更干净，不保留无意义的空 `div`。
- 日志阅读路径更直接，像单一会话输出窗口。

缺点：

- 会失去点击切换单条日志的能力。

### 5.2 备选方案：隐藏旧列表，仅保留旧逻辑

- 样式上隐藏左侧日志列表，但保留双栏 DOM 和选中逻辑。

优点：

- 改动小。

缺点：

- 逻辑与结构不一致，会留下死节点与死状态。

## 6. 页面结构调整

### 6.1 顶部卡片

右侧顶部区域继续保持双列网格：

1. `workspace-primary-card`
2. `workspace-response-card`

调整规则如下：

- 同一行中两张卡片拉伸为等高。
- 卡片内部内容保持原有排列顺序。
- 卡片内部的代码块继续独立滚动。

### 6.2 Logs 面板

`Logs` 面板结构调整为：

- 面板标题区
- 单一日志会话框

删除以下旧结构：

- `request-log-list`
- `selectedLogId`
- “点击日志项查看详情”的交互路径

保留以下展示语义：

- 会话级请求历史
- 默认空状态文案
- 新请求优先显示在顶部

## 7. 渲染规则

### 7.1 顶部等高规则

桌面端下：

- `workspace-main-grid` 的两个直接子卡片必须在同一网格行拉伸到一致高度。
- `workspace-response-card` 需要补齐为纵向布局容器，以便内部内容在固定高度下自然分布。

窄屏下：

- 双列回退为单列。
- 不强制等高。

### 7.2 日志会话框规则

日志区域遵循以下规则：

- 无日志时：显示默认空状态文案。
- 有日志时：按 `state.requestLogs` 当前顺序直接渲染全部日志文本。
- 由于当前实现已通过 `unshift` 将最新日志放在数组头部，因此最终输出天然为时间倒序。

每条日志建议包含以下信息：

- 时间
- 接口名
- 方法
- 状态
- 耗时
- URL
- Request Body
- Response 或 Error

多条日志之间加入清晰分隔线，便于在单一会话框中连续阅读。

## 8. 状态与逻辑调整

### 8.1 `app.js`

需要调整的状态与逻辑如下：

- 删除 `selectedLogId` 状态字段。
- 删除 `getSelectedLog()` 逻辑。
- 删除 `requestLogList` DOM 引用与点击事件。
- `renderRequestLogs()` 改为把全部日志记录格式化并写入单一 `pre`。
- `createLogEntry()` 与 `updateLogEntry()` 保持不变，仅改变最终展示方式。

### 8.2 `index.html`

需要调整的结构如下：

- 删除 `request-log-list` 对应 `div`。
- `log-layout` 降级为单列容器，或直接移除双栏语义类。

### 8.3 `styles.css`

需要调整的样式如下：

- 顶部两张卡片所在网格使用拉伸对齐。
- `workspace-response-card` 调整为与左卡一致的纵向卡片容器。
- 删除或废弃 `request-log-list`、`log-item`、`log-item-header`、`log-item-meta`、`log-item-name` 这类仅服务于左侧列表的样式。
- `log-detail` 作为唯一日志会话框，承担最大高度与内部滚动。

## 9. 风险与兼容性

主要风险如下：

- 旧日志列表相关样式和状态若未清理干净，会留下无效代码。
- 如果日志文本一次性过长，需要确保 `pre` 的内部滚动仍然稳定。
- 顶部等高后，如果右侧响应为空而左侧内容较多，需要确认视觉上不会显得过空。

兼容性原则：

- 不改变请求发送与响应处理链路。
- 不改变日志记录对象结构。
- 只改变展示结构与样式。

## 10. 测试与验证

至少覆盖以下场景：

1. 页面静态结构：
   - 不再包含 `request-log-list`。
   - 保留单一日志输出区域。
2. 无日志状态：
   - 日志框显示默认文案。
3. 单条日志状态：
   - 日志框显示完整摘要。
4. 多条日志状态：
   - 最新日志位于最上方。
   - 各条日志之间存在文本分隔。
5. 顶部卡片布局：
   - 桌面端下 `Request` 与 `Response` 视觉等高。
   - 移动端回退为单列。

## 11. 实施结论

本次增量方案以“顶部对齐、日志合流、结构收敛”为核心原则，在不改变业务逻辑的前提下，降低右侧工作区的视觉断层和日志理解成本。

实现阶段应优先保证：

1. 顶部两张卡片稳定等高。
2. 日志面板只保留一个会话框。
3. 旧日志列表状态和样式清理彻底。
4. 自动化测试同步收敛。
