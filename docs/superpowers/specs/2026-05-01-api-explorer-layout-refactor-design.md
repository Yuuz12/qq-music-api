# API Explorer 页面结构重构 Spec

## 1. 文档目标

本 Spec 定义 `.worktrees/api-explorer` 中 API Explorer 前端页面的结构重构方案，目标是在不改变现有后端元数据接口协议的前提下，把当前“顺序卡片式调试页”升级为更适合高频调试的工作台布局。

本次变更只覆盖 Explorer 前端入口与主页面结构，重点解决以下问题：

- 接口数量增多后，仅靠下拉选择不利于快速定位目标接口。
- 请求调试链路缺少会话级请求日志，无法回看前几次请求结果。
- 目前页面的请求方法信息只在详情摘要里出现，无法用于过滤接口列表。
- 首页入口较弱，无法清晰传达“进入 Explorer 调试台”的主路径。

## 2. 背景与现状

当前 API Explorer 由以下静态资源组成：

- `public/explorer/index.html`：页面骨架，包含 Hero、接口选择、参数输入、请求预览、响应结果四块区域。
- `public/explorer/app.js`：负责拉取 `/explorer/metadata`、生成动态表单、构造请求并展示响应。
- `public/explorer/styles.css`：提供基础卡片和双列样式。
- `public/index.html`：服务启动后的默认入口页，当前仅提供简单文案和 Explorer 链接。

当前实现具备以下能力：

- 基于 `/explorer/metadata` 动态生成接口下拉选项。
- 根据 `pathParams`、`queryParams` 和 `bodyExample` 渲染输入控件。
- 支持 `GET` 与 `POST` 请求发送。
- 可以展示请求预览、响应状态和响应内容。

当前实现的主要不足：

- 接口入口只有一个 `select`，在全量接口下定位效率低。
- 页面是“自上而下”的线性阅读结构，不适合频繁切换接口与重复调试。
- 没有请求历史，用户只能看到最近一次响应。
- 请求方法没有独立过滤能力，无法快速只看 `GET` 或 `POST`。

## 3. 目标

本次页面重构目标如下：

1. 将 Explorer 改造成“左侧接口目录 + 右侧调试工作台”的布局。
2. 在左侧接口目录中支持接口搜索。
3. 在左侧接口目录中支持按请求方法过滤，至少覆盖 `All`、`GET`、`POST`。
4. 在右侧工作台中新增会话级请求日志展示，支持回看本次会话的请求结果。
5. 保持现有 `/explorer/metadata` 协议不变，避免本次工作扩散到服务端元数据结构调整。
6. 同步升级 `public/index.html`，让默认入口页更明确地把用户引导到 Explorer。

## 4. 非目标

以下内容不在本次改造范围内：

- 修改 `src/config/apiExplorer.ts` 中的接口元数据字段结构。
- 新增服务端持久化日志或把请求历史写入文件。
- 增加接口收藏、分类折叠、拖拽布局或多标签调试。
- 引入前端框架或重构为 React/Vue 应用。
- 实现跨会话日志恢复或本地存储同步。

## 5. 方案选型

本次采用 `方案 A：左侧接口目录 + 右侧调试工作台`。

### 5.1 备选方案

#### 方案 A：工作台布局

- 左侧固定接口目录，承载搜索、方法过滤和接口列表。
- 右侧为当前接口的详情、参数表单、请求预览、响应结果和请求日志。

优点：

- 最符合“频繁切换接口并反复调试”的使用场景。
- 搜索、过滤、切换接口的路径短。
- 请求日志可以与当前接口详情并列展示，信息组织清晰。

缺点：

- 需要重写主页面 DOM 结构和前端状态管理代码。

#### 方案 B：顶部筛选 + 下方详情

- 顶部一行放搜索和过滤，下方继续沿用当前卡片式结构。

优点：

- 改动较小。

缺点：

- 仍然是纵向流程页面，接口列表浏览效率一般。
- 请求日志在视觉上容易被压缩到页面底部。

#### 方案 C：保留当前结构，只追加功能

- 维持下拉选择接口，仅增加搜索、过滤和日志区域。

优点：

- 实现风险最低。

缺点：

- 结构性问题无法解决，下拉框仍然是主要瓶颈。

### 5.2 选择原因

选择方案 A 的原因如下：

- 用户已明确偏好“左侧列表右侧详情”的调试工作台结构。
- 当前元数据已包含 `name`、`category`、`method`、`path`，足以驱动左侧接口目录。
- 请求日志与当前请求结果并置展示时，最符合调试时的对比和回看需求。

## 6. 页面信息架构

重构后的页面分为两个主要层级：

### 6.1 入口页

`public/index.html` 升级为更明确的导航入口页，承担以下职责：

- 展示项目名称和服务已就绪状态。
- 提供“打开 API Explorer”的主操作按钮。
- 保留在线文档入口。
- 展示 2 到 3 个示例接口链接，作为快速试用入口。

入口页不承担调试功能，只负责引导。

### 6.2 Explorer 主页面

`public/explorer/index.html` 调整为两栏工作台：

- 左侧 `sidebar`：
  - 页面标题和说明
  - 接口搜索输入框
  - 请求方法过滤器
  - 接口统计摘要
  - 接口列表
- 右侧 `workspace`：
  - 当前接口概览
  - 参数表单
  - 请求预览
  - 响应结果
  - 请求日志

在窄屏场景下，两栏结构退化为上下堆叠，左侧目录置顶。

## 7. 组件拆分设计

本次不引入组件框架，但会在原生 JS 中做职责拆分，避免单一函数持续膨胀。

### 7.1 左侧目录区

左侧目录由以下模块构成：

- `search input`：实时匹配接口名称、分类、路径。
- `method filter`：切换 `All`、`GET`、`POST`。
- `endpoint list`：展示过滤后的接口条目。
- `selection summary`：展示当前筛选命中的数量和当前激活接口。

接口条目展示字段：

- 接口名
- 分类
- 请求方法
- 路径

当前激活接口在列表中要有明显高亮。

### 7.2 右侧工作台

右侧工作台分为五个区域：

1. `endpoint overview`
   - 展示接口名称、描述、分类、方法、路径。
2. `request form`
   - 按路径参数、查询参数、请求体分组渲染。
3. `request preview`
   - 展示当前即将发送的请求方法、URL 和可选请求体。
4. `response result`
   - 展示最近一次发送请求的状态、耗时和响应内容。
5. `request logs`
   - 展示当前会话中的请求历史，可回看单次请求的摘要信息。

## 8. 状态模型设计

为支持搜索、过滤和请求日志，页面状态扩展为以下结构：

- `metadata`：服务端返回的 Explorer 元数据。
- `endpointMap`：按 `id` 建立的接口索引。
- `activeEndpointId`：当前激活接口。
- `searchKeyword`：接口搜索关键字。
- `methodFilter`：当前方法过滤条件，默认 `All`。
- `visibleEndpointIds`：当前搜索和过滤后可见的接口列表。
- `requestLogs`：本次会话中的请求日志数组。
- `selectedLogId`：当前被查看的日志记录。

设计原则：

- 搜索和方法过滤只影响左侧接口列表，不直接清空右侧日志。
- 当前激活接口如果被过滤条件排除，则自动切换到过滤结果中的第一个接口。
- 请求日志是前端内存态数据，仅在页面生命周期内存在。

## 9. 搜索与过滤规则

### 9.1 搜索规则

搜索输入框采用大小写不敏感的包含匹配，匹配字段包括：

- `endpoint.name`
- `endpoint.category`
- `endpoint.path`

匹配逻辑：

- 去除前后空格后再比较。
- 空字符串表示不过滤。
- 不做拼音、模糊纠错或高亮分词，保持首版简单可控。

### 9.2 方法过滤规则

方法过滤器提供三个选项：

- `All`
- `GET`
- `POST`

过滤逻辑：

- `All` 时保留全部接口。
- 选择具体方法时，只显示 `endpoint.method` 完全匹配的接口。

### 9.3 空状态规则

当搜索和过滤后无结果时：

- 左侧列表显示空状态提示。
- 右侧工作台保留上一次激活接口的内容，直到用户清空过滤或重新选择其他结果。

该规则可避免用户在输入搜索词时右侧区域闪烁或突然清空。

## 10. 请求日志设计

本次新增“会话历史明细”请求日志区。

### 10.1 日志记录时机

每次点击“发送请求”并真正触发网络请求时，都新增一条日志记录。

日志在两个阶段更新：

1. 请求刚发起时，先写入 `pending` 状态记录。
2. 请求成功或失败后，再回填状态码、耗时和响应摘要。

### 10.2 日志字段

每条日志记录至少包含：

- `id`：前端生成的唯一标识。
- `timestamp`：发起请求的时间。
- `endpointId`：对应接口 ID。
- `endpointName`：接口名称。
- `method`：请求方法。
- `url`：最终请求地址。
- `requestBody`：请求体文本，仅 `POST` 时存在。
- `status`：`pending`、HTTP 状态码或 `error`。
- `duration`：请求耗时。
- `responsePreview`：响应摘要文本或格式化后的 JSON 字符串。
- `errorMessage`：网络异常时记录的错误消息。

### 10.3 日志展示

日志区采用“列表 + 明细摘要”的轻量模式：

- 列表中展示时间、方法、接口名、状态、耗时。
- 当前查看日志高亮显示。
- 点击某条日志后，右侧下方的日志详情区展示：
  - 请求 URL
  - 请求体
  - 响应摘要或错误信息

如果当前没有日志：

- 显示“发送请求后将在这里看到会话历史”。

## 11. 前端代码结构设计

`public/explorer/app.js` 需要从“单文件串行流程”改造成按职责分组的函数集合。

推荐拆分如下：

- `state helpers`
  - 获取当前接口
  - 获取当前可见接口
  - 更新搜索和过滤状态
- `filter helpers`
  - 根据搜索关键字和方法过滤计算结果
- `form helpers`
  - 创建输入控件
  - 渲染表单分组
  - 收集表单值
- `request helpers`
  - 构造 URL
  - 校验必填项
  - 构造请求预览
- `log helpers`
  - 创建日志记录
  - 更新日志记录
  - 渲染日志列表和日志详情
- `render helpers`
  - 渲染左侧接口列表
  - 渲染接口概览
  - 渲染请求预览
  - 渲染响应结果
  - 渲染空状态
- `event bindings`
  - 搜索输入事件
  - 方法过滤点击事件
  - 接口列表切换事件
  - 发送请求事件

本次允许继续使用 IIFE 结构，但要求内部函数分区更清晰，减少直接操作全局 DOM 的散落逻辑。

## 12. HTML 结构设计

`public/explorer/index.html` 重构后应满足以下结构目标：

- 以 `app-shell` 作为整体容器。
- 左侧使用语义化的 `aside` 承载接口目录。
- 右侧使用 `main` 承载调试工作台。
- 请求预览、响应结果、请求日志各自为独立 panel。
- 页面仍保留返回首页和在线文档的导航入口。

HTML 需为后续 JS 渲染预留稳定的元素锚点，至少包括：

- 搜索输入元素
- 方法过滤容器
- 接口列表容器
- 接口空状态容器
- 当前接口标题与描述容器
- 请求表单容器
- 请求预览容器
- 响应状态和响应内容容器
- 日志列表容器
- 日志详情容器

## 13. 样式设计边界

本轮实现会配套调整 `styles.css`，但样式目标保持克制：

- 以高可读性和空间分区清晰为主。
- 强化左侧列表与右侧内容区的层级关系。
- 通过颜色区分 `GET`、`POST`、成功、失败和进行中状态。
- 移动端回退为单列布局，保证表单和响应可读。

样式不是本次设计的主要风险点，因此不要求引入设计系统或复杂动画。

## 14. 错误处理与边界条件

### 14.1 参数校验

发送请求前继续沿用当前必填参数校验逻辑，并补充以下行为：

- 校验失败时写入响应区错误提示，但不新增请求日志。
- `POST` 请求体不是合法 JSON 时，阻止请求并展示解析错误。

### 14.2 过滤结果为空

当左侧没有匹配接口时：

- 接口列表展示空状态。
- 发送按钮保持可用，但其行为仍基于当前激活接口。
- 不自动清空表单和响应内容。

### 14.3 网络错误

请求失败时：

- 响应区显示失败状态与错误信息。
- 对应日志记录标记为 `error`。
- 日志详情中保留请求 URL 和错误消息，方便排查。

## 15. 测试设计

本次重构以页面结构和前端状态逻辑为核心，测试重点如下：

### 15.1 单元测试

新增或扩展前端纯函数测试，重点覆盖：

- 搜索匹配逻辑
- 方法过滤逻辑
- 请求日志创建和更新逻辑
- 日志列表选择逻辑

如果当前结构不便于直接测试，应优先把可测的纯逻辑抽到独立工具函数中，而不是强行为 DOM 代码补低价值测试。

### 15.2 功能验证

手工验证至少覆盖以下场景：

1. 启动服务后，从首页进入 Explorer。
2. 在左侧搜索接口名，列表正确过滤。
3. 切换 `GET` 或 `POST` 过滤器后，列表正确更新。
4. 选择一个接口并成功发起请求。
5. 请求完成后，在日志区看到新增历史记录。
6. 点击历史记录，能够查看该次请求的摘要。

### 15.3 发布门禁

需满足以下结果：

- `npm run lint`
- `npm test`
- 必要的手工功能验证

并确保最终结果满足：

- `linter_result`: pass
- `unit_test_result`: pass
- `func_test_result`: pass
- `status`: 成功

## 16. 实施边界

本次代码改造优先覆盖以下文件：

- `public/index.html`
- `public/explorer/index.html`

## 17. 风险与应对

### 风险 1：`app.js` 继续膨胀

应对：

- 先按职责拆分函数区块。
- 如果仍然过长，再把纯逻辑抽离到独立工具文件。

### 风险 2：搜索与切换接口状态相互影响

应对：

- 明确“过滤只影响列表，不主动清空工作台”的状态规则。
- 用单一入口函数统一处理过滤结果和激活接口同步。

### 风险 3：请求日志与响应区信息重复

应对：

- 响应区只展示“最近一次请求”结果。
- 日志区负责展示会话历史和某条记录的摘要回看，职责分离。

## 18. Spec 自检

自检结论如下：

- 已明确本次只做前端页面重构，不扩展到服务端协议改造。
- 搜索、方法过滤、请求日志和入口页升级都已纳入范围。
- 请求日志字段、状态规则和空状态行为已显式定义。
- 无 `TODO`、`TBD` 或含糊边界描述。
