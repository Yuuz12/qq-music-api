# API Explorer 专业化工作台与首页视觉收敛 Spec

## 1. 文档目标

本 Spec 定义 `.worktrees/api-explorer` 中 API Explorer 与首页的下一轮增量重构方案。

本轮重点不再是“顶部 Header + 右侧多选 Tab 网格工作区”，而是继续向更稳定、更专业的 API 工具体验收敛：

1. 缩小顶部 Header 的屏占比，减少无效大块留白。
2. 统一首页与 Explorer 的视觉语言，提升专业感和产品感。
3. 将右侧工作区收敛为固定布局，而不是继续保留多选显示控制。
4. 将原 `Overview` 与 `Request` 合并成单一主操作区。
5. 删除独立 `History` 区域，改为底部整行日志区。

## 2. 背景与现状

当前 Explorer 已完成以下工作：

- 页面顶层已调整为 `header + sidebar + workspace` 的三段式结构。
- 顶部已有品牌、标题、描述和外链入口。
- 右侧已存在 `Overview`、`Request`、`Response`、`History` 四个模块。
- 右侧工作区已支持通过多选 tab chips 控制多个模块显示，并按 2 列网格排布。

当前版本仍存在的问题：

- 顶部 Header 内容块占比偏大，首屏视觉重心过高，削弱了工作区的主体性。
- 首页仍然更接近“欢迎页”或“跳转页”，专业工具产品感不足。
- 右侧多选 tab 虽然灵活，但增加了结构自由度，也带来了认知成本。
- `Overview` 与 `Request` 分离后，用户在“理解接口”与“配置请求”之间仍然需要跨卡片跳转。
- `History` 作为独立卡片占据主工作区位置，但语义上更适合下沉为日志轨迹区。
- 顶部 `Workspace` 显示控制条在本轮目标下不再必要。

## 3. 目标

本次工作的目标如下：

1. 将 Explorer 顶部 `Header` 收敛成更紧凑的专业产品头栏。
2. 让首页与 Explorer 共享统一的极简专业视觉语言。
3. 将右侧工作区重构为“上部双栏主区 + 下部整行日志区”的固定布局。
4. 将 `Overview` 与 `Request` 合并为单一主操作区。
5. 保留 `Response` 作为独立结果区。
6. 将原 `History` 的能力整合到底部 `Logs` 区，删除独立 `History` 卡片。
7. 删除 `Workspace` 顶部多选显示控制区。
8. 提升版式对齐、信息密度和细节质感，使页面更像正式 API 控制台。

## 4. 非目标

以下事项不在本次工作范围内：

- 修改 `/explorer/metadata` 数据协议。
- 修改后端路由、控制器或日志上报链路。
- 引入新的前端框架或新的页面路由体系。
- 为工作区增加拖拽排序、自定义布局或跨会话布局持久化。
- 引入重品牌化官网视觉或营销型动效。
- 修改日志记录的数据结构本身。

## 5. 方案选型

本次采用 `方案 B：极简专业工具台`。

### 5.1 方案 A：压缩式微调

- 保留当前多选 tab 网格结构，仅缩小 Header、删除少量区域并微调样式。

优点：

- 改动成本最低。
- 能快速解决“头部过大”的局部问题。

缺点：

- 无法从根本上解决右侧信息路径偏散的问题。
- 专业感提升有限，页面仍会保留较强的“可拼接模块”气质。

### 5.2 方案 B：极简专业工具台

- 顶部 Header 收敛为精炼品牌条。
- 首页升级为更正式的产品入口页。
- Explorer 右侧采用“主操作区 + 响应区 + 底部日志区”的固定工作流布局。

优点：

- 能同时满足“更专业”和“稍微更有特色”的双重目标。
- 让阅读顺序与操作顺序保持一致。
- 删除不必要的布局自由度后，整体更稳定、更像正式开发工具。

缺点：

- 需要替换已有多选 tab 显隐模型。
- 需要同步更新首页、Explorer DOM 结构、样式和相关测试。

### 5.3 方案 C：强品牌展示型

- 在首页和 Explorer 都引入更强的品牌视觉，比如更明显的渐变、装饰背景和更大头图区域。

优点：

- 视觉记忆点更强。

缺点：

- 容易削弱工具属性。
- 改动范围大，且不符合当前“极简专业”的主方向。

### 5.4 选择原因

选择方案 B 的原因如下：

- 用户明确希望“更专业”，而不是更花哨。
- 该方案既能压缩头部占比，也能重构主工作区的信息路径。
- 底部日志区更符合调试工具中的控制台语义。
- 首页与 Explorer 可以在同一视觉语言下形成一致体验。

## 6. 页面信息架构

### 6.1 顶部 Header

顶部保留独立 `header.app-header`，但改为低高度、紧凑化结构，仅承载：

- 品牌标识
- 页面标题
- 一行描述
- 返回首页
- 在线文档

设计原则：

- Header 负责全局上下文，不再承担工作区控制职责。
- 通过更短的高度和更高的信息密度，让视觉焦点自然落回工作区。
- 可保留极淡的品牌高光或光晕，但只能作为气质增强。

### 6.2 左侧 Sidebar

左侧继续使用 `section.sidebar` 作为导航区，承载以下内容：

- 搜索框
- 请求方法过滤器
- 结果统计
- 当前激活接口提示
- 接口列表

设计原则：

- 左侧只承担接口发现与切换。
- 不混入请求配置、响应结果或日志信息。
- 保持“顶部筛选固定、列表区域滚动”的既有交互。

### 6.3 右侧 Main Workspace

右侧工作区改为固定两层结构：

1. `workspace-main-grid`
2. `workspace-log-card`

其中：

- `workspace-main-grid` 为上层双栏布局。
- `workspace-log-card` 为底部整行日志区。

### 6.4 上层双栏结构

上层双栏固定包含两个核心卡片：

- `workspace-primary-card`
- `workspace-response-card`

#### `workspace-primary-card`

作为主操作区，合并原：

- `Overview`
- `Request`

承载以下内容：

- 当前接口名称与描述
- 分类 / 方法 / 路径等元信息
- 路径参数、查询参数、Body JSON
- 请求摘要
- 发送请求按钮

#### `workspace-response-card`

作为结果区，承载以下内容：

- 最近一次请求的状态码
- 耗时
- 响应正文

### 6.5 底部日志区

底部新增固定 `workspace-log-card`，承担原 `History` 的信息能力：

- 当前会话请求列表
- 当前选中日志详情

语义原则：

- `Response` 负责展示最近一次结果。
- `Logs` 负责展示整个会话的连续请求轨迹。
- 两者互补，不相互覆盖。

### 6.6 删除的区域

以下区域在本轮中删除：

- `Workspace` 顶部显示控制区
- 独立 `History` 卡片
- 顶层多选 tab 切换交互

## 7. 视觉风格与版式细节

### 7.1 视觉关键词

本轮视觉关键词如下：

- 极简专业
- 工具化
- 高对齐
- 轻品牌感

目标效果：

- 第一眼像正式 API 控制台，而不是欢迎页或文档附属页。
- 通过比例、秩序和交互细节建立专业感，而不是依赖大块装饰。

### 7.2 全局视觉语言

视觉语言采用浅色专业底，特点如下：

- 页面背景使用非常浅的冷灰蓝底色或轻微渐变。
- 卡片表面使用高亮浅色面。
- 边框采用低对比细描边。
- 强调色延续品牌蓝紫系，但仅用于按钮、焦点态和状态点缀。

风格约束：

- 阴影轻量，避免厚重悬浮感。
- 圆角分级统一，减少拼装感。
- 过渡动效克制，只保留必要的 hover 与 focus 平滑反馈。

### 7.3 Header 版式

Explorer 顶部 Header 的具体要求如下：

- 明显减小整体高度。
- 左侧保留 `QQ Music API` eyebrow 和主标题。
- 描述压缩为一行，强调“本地 API 调试工作台”语义。
- 右侧仅保留 `返回首页` 与 `在线文档` 两个轻量操作。
- 链接样式升级为更精致的文本按钮或轻按钮。

### 7.4 首页版式

首页由“服务已就绪提示页”升级为“正式产品入口页”：

- Hero 区高度收紧，避免大面积空白。
- `打开 API Explorer` 为唯一主按钮。
- `在线文档` 为次按钮。
- Hero 下方以 2 到 3 个能力卡片或快捷能力说明补足产品感。
- “快速试用”入口保留，但降为辅助信息层级。

### 7.5 Explorer 主区版式

Explorer 主区的版式要求如下：

- 上层双栏固定布局：
  - 左侧主操作区
  - 右侧响应区
- 下层为整行日志区
- 桌面端优先保持双栏
- 窄屏时降级为“主操作区 -> 响应区 -> 日志区”的单列顺序

### 7.6 卡片密度与组件风格

卡片和内部组件的风格要求如下：

- 标题区 padding 收紧，减少空白占比。
- Meta 信息以 badge 或 meta row 统一展示。
- 请求摘要、响应体和日志详情使用统一 code block 风格。
- 空状态文案保持简短专业，避免大段解释性说明。
- 方法、状态、分类等标签风格统一。

### 7.7 特色表达边界

允许保留少量特色细节，但需要严格克制：

- 极淡品牌光晕
- 主按钮细腻高光或描边
- 卡片顶部极细渐变描边
- 更利落的输入框 focus 态

这些细节只能增强专业感，不能把页面做成营销页。

## 8. 组件职责、状态模型和交互规则

### 8.1 组件职责

#### `Header`

- 展示品牌、标题、短描述和全局导航。
- 不再承载 workspace 显示控制。

#### `Sidebar`

- 负责接口搜索、过滤、列表和切换。
- 不承担请求配置或日志展示。

#### `Main Workspace`

- 负责当前接口的完整调试流程。
- 固定由主操作区、响应区和日志区构成。

#### `Primary Workspace`

- 合并 `Overview` 与 `Request`。
- 提供“理解接口 -> 配置参数 -> 查看请求摘要 -> 发送请求”的完整闭环。

#### `Response Workspace`

- 展示最近一次请求结果。

#### `Logs Workspace`

- 展示当前会话日志列表与选中日志详情。

### 8.2 模块合并与删除

本轮模块调整如下：

- `Overview` + `Request` -> `Primary Workspace`
- `Response` 保留为独立结果区
- `History` 能力保留，但视觉并入底部 `Logs`
- 删除 `Workspace` 顶部控制条
- 删除独立 `History` 卡片
- 删除顶层多模块显隐逻辑

### 8.3 主操作区内部结构

主操作区从上到下按以下顺序组织：

1. 当前接口头部
2. 参数配置区
3. 请求摘要区
4. 操作区

详细内容如下：

- 当前接口头部展示接口名称、描述、分类、方法和路径。
- 参数配置区展示路径参数、查询参数和 Body JSON。
- 请求摘要区实时生成最终请求信息。
- 操作区提供发送请求按钮和必要的轻量状态提示。

### 8.4 需要删除的状态

删除以下顶层状态与相关逻辑：

- `visibleWorkspaceTabs`
- 顶部 workspace tab 渲染逻辑
- “至少保留一个 tab 可见”的约束逻辑
- workspace 卡片显隐计算逻辑

### 8.5 继续保留的状态

继续保留以下业务状态：

- `metadata`
- `endpointMap`
- `activeEndpointId`
- `searchKeyword`
- `methodFilter`
- `visibleEndpointIds`
- `requestLogs`
- `selectedLogId`

### 8.6 继续保留的请求内部状态

继续保留请求编辑器相关状态，包括：

- 参数输入状态
- Body 文本状态
- 请求摘要生成状态
- `requestSectionState`

约束如下：

- `requestSectionState` 仅服务主操作区内部的子区块显隐。
- 不再影响顶层布局结构。

### 8.7 交互规则

#### 接口切换

点击左侧接口后：

- 主操作区头部立即切换到新接口信息。
- 参数区按新接口元数据重建。
- 请求摘要同步更新。
- `Response` 恢复到等待态。
- `Logs` 保留当前会话轨迹，不因切换接口而清空。

#### 参数编辑

编辑任何参数后：

- 请求摘要实时更新。
- 不自动发送请求。
- 输入错误在发送前或输入过程中给予轻量提示。

#### 发送请求

点击发送后：

- `Response` 进入加载态。
- 请求结束后更新状态码、耗时和响应正文。
- 同时向 `Logs` 追加一条记录。
- 新增日志默认成为当前选中项。

#### 查看日志

点击任意日志项后：

- 底部日志详情切换为该条记录。
- 不覆盖 `Response` 当前显示内容。
- `Response` 继续代表最近一次发送结果。
- `Logs` 详情代表当前会话中被选中的任意记录。

### 8.8 空状态与边界条件

#### 当前接口无额外参数

- 参数区显示简洁空状态。
- 请求摘要和发送按钮仍然保留。

#### 尚未发送请求

- `Response` 显示等待态，文案保持简短专业。

#### 当前会话无日志

- `Logs` 显示空列表态和简洁说明。

#### 请求失败

- `Response` 展示错误状态和异常摘要或响应体。
- `Logs` 仍记录失败请求。

#### 服务未启动或网络异常

- `Response` 展示明确错误提示。
- `Logs` 中记录失败条目。

## 12. 错误处理与边界条件

### 12.1 删除 workspace 控制区后的行为

由于顶层布局改为固定结构：

- 页面不再支持切换主模块显隐。
- 页面切换接口或发送请求时，不会产生布局跳动。

### 12.2 Response 与 Logs 的职责边界

- `Response` 只表示最近一次请求结果。
- `Logs` 表示当前会话轨迹。
- 点击旧日志详情时，不应回写覆盖 `Response`。

### 12.3 无参数接口

当当前接口无需参数时：

- 主操作区显示空态提示。
- 请求摘要继续可见。
- 发送请求按钮仍可直接使用。
