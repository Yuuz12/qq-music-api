# 轻量 API Explorer 与 Worktree 开发模式 Spec

## 1. 文档目标

本 Spec 定义 `qq-music-api` 仓库内“启动项目后自动打开一个可视化接口测试页面，并采用 `git worktree` 模式开发”的设计方案、实施边界与验证标准。

本次目标不是把项目一次性升级为完整的 OpenAPI 平台，而是在尽量少引入额外复杂度的前提下，为当前 Koa API 提供一个可直接输入参数、触发请求、查看响应结果的本地可视化调试入口，并让后续实现过程在独立 `worktree` 中完成，避免污染当前主工作区。

## 2. 背景与上下文

当前仓库具备以下基础：

- 服务端入口位于 `src/app.ts`，当前通过 `npm run dev` 启动 `ts-node-dev` 运行 Koa 服务。
- 路由集中定义在 `src/routes/router.ts`，当前接口主要以 `GET` 为主，存在少量 `POST` 接口。
- 接口参数主要通过路径参数和查询参数传入，尚未建立统一的接口元数据层。
- 仓库已有 `docs/` 目录，并通过 `docsify` 提供文档站点能力，`package.json` 中已存在 `npm run docs` 脚本。
- 当前启动 API 后仅输出本地地址日志，不会自动打开浏览器，也没有 Swagger、Redoc 或其他接口可视化测试页面。

当前主要问题：

- 接口使用者只能手动拼接 URL 测试，效率较低。
- 路由虽然集中，但缺少一份机器可读的接口描述，无法直接生成参数输入表单。
- 若直接在当前工作区实现，会与已有未提交改动混合，影响隔离性和后续提交管理。

## 3. 目标

本次工作的目标如下：

1. 在本地启动项目后，自动打开一个可视化接口测试页面。
2. 页面支持从接口列表中选择接口，并输入路径参数、查询参数或请求体参数。
3. 页面支持发起请求并展示请求地址、状态码和格式化后的响应内容。
4. 保持实现轻量，优先复用现有 `docs/` 或静态资源能力，不强制引入完整 OpenAPI 体系。
5. 后续实现工作通过独立 `git worktree` 目录和功能分支完成。
6. 保证实现具备可测试性，且不在 `test` 环境中触发自动打开浏览器等副作用。

## 4. 非目标

以下事项不在本次工作直接承诺范围内：

- 为所有接口补齐完整 OpenAPI Schema、响应模型和示例。
- 引入 Swagger UI、Redoc、Stoplight 等完整标准文档栈。
- 搭建独立的 React/Vite 调试前端项目。
- 实现鉴权管理、接口分组权限或生产环境在线文档托管。
- 自动推导所有复杂参数类型并生成完整表单校验规则。

## 5. 方案选型

本次采用 `方案 A：基于现有文档体系扩展轻量 API Explorer`。

### 5.1 备选方案

#### 方案 A：`Docsify + 自定义 API Explorer`

- 在 `docs/` 下新增一个轻量静态调试页面。
- 由项目提供一份接口元数据，供页面渲染接口列表与参数输入表单。
- 启动开发脚本时自动打开 Explorer 页面。

优点：

- 与现有 `docs/` 基础设施兼容。
- 改动面可控，学习成本低。
- 页面可按当前项目接口特点定制，适配路径参数场景。

缺点：

- 不属于标准 OpenAPI 文档。
- 接口元数据需要手工维护。

#### 方案 B：`public/` 静态调试页

- 将纯 HTML/JS 调试页直接放入 `public/`，由 Koa 静态托管。

优点：

- 实现最轻。
- 只需要启动一个服务。

缺点：

- 与已有 `docs/` 文档体系割裂。
- 页面结构和文档入口不统一，后续扩展性一般。

#### 方案 C：独立前端应用

- 新增单独前端工程，构建更丰富的接口调试站点。

优点：

- 体验最好，扩展性最强。

缺点：

- 明显超出当前需求。
- 增加额外构建链路、脚本和维护成本。

### 5.2 选择原因

选择方案 A 的原因如下：

- 当前仓库已经存在 `docs/` 能力，复用成本最低。
- 用户明确偏好“快速测试接口 + 参数输入”，而不是完整标准化文档。
- 当前路由以路径参数为主，自定义 Explorer 更容易按项目实际接口结构做适配。
- 方案 A 同时兼顾低成本实现、可视化入口和后续扩展空间。

## 6. 总体设计

整体设计拆分为四个部分：

1. `git worktree` 开发隔离层
2. 接口元数据层
3. 轻量 API Explorer 页面
4. 启动与自动打开浏览器机制

### 6.1 Worktree 设计

实现前先创建独立 `git worktree`，用于承载本次功能开发。

建议约定：

- 新分支命名：`feat/api-explorer`
- 新 worktree 目录命名：与仓库主目录同级或约定的 `worktrees/` 目录下，例如 `../qq-music-api-api-explorer`

目标效果：

- 当前主工作区保持不变。
- 新功能在独立目录中实现、运行和验证。
- 后续提交仅包含本次功能相关改动，降低与当前未提交改动冲突的概率。

### 6.2 接口元数据层设计

由于现有 `koa-router` 仅定义路径与处理函数，无法直接驱动表单生成，因此需要新增一层轻量接口元数据。

元数据至少包含：

- `id`：接口唯一标识
- `name`：页面展示名称
- `method`：HTTP 方法
- `path`：原始路由模板
- `category`：接口分类，例如搜索、歌曲、歌手
- `description`：简短说明
- `pathParams`：路径参数描述
- `queryParams`：查询参数描述
- `bodySchema`：请求体字段描述，仅用于少量 `POST` 接口
- `example`：可选的默认示例值

每个参数描述至少包含：

- `key`
- `label`
- `required`
- `defaultValue`
- `placeholder`
- `description`

该元数据层是“页面驱动数据”，不是完整的接口协议系统，重点满足以下需求：

- 生成参数输入表单
- 拼装最终请求地址
- 给出合理默认值，减少手工输入
- 为常用接口提供最小可用说明

### 6.3 API Explorer 页面设计

Explorer 页面作为一个轻量静态页面，建议放在 `docs/` 目录内，并在文档导航中增加入口。

页面核心区域包括：

- 接口选择区：支持按分类浏览或直接选择接口
- 参数表单区：按路径参数、查询参数、请求体分组输入
- 请求预览区：展示实际即将发送的 URL、方法和 Body
- 响应展示区：展示状态码、耗时和格式化 JSON

页面核心交互如下：

1. 用户选择一个接口。
2. 页面根据接口元数据渲染参数输入表单。
3. 用户输入参数或使用默认值。
4. 页面构造最终请求。
5. 用户点击“发送请求”。
6. 页面发起请求并展示结果。

页面设计原则：

- 默认只提供本地调试所需能力，不增加复杂视觉装饰。
- 优先保证“能快速发请求、能看清参数、能看懂返回”。
- 对空值、必填项和错误返回做基础提示。

### 6.4 启动与自动打开浏览器设计

需要新增开发启动脚本，使启动项目时自动打开 Explorer 页面。

推荐行为：

- 启动 API 服务成功后，自动打开本地 Explorer 地址。
- 若文档服务需要单独运行，则由启动脚本并行启动 API 服务和文档服务。
- 若 Explorer 可由 API 静态托管直接访问，则只需启动一个服务。

自动打开浏览器的触发约束：

- 仅在非 `test` 环境触发。
- 仅在开发启动脚本中触发，不在生产模式默认触发。
- 打开失败不阻塞 API 服务启动，只记录日志。

## 7. 推荐落地方式

基于当前仓库结构，推荐以下落地方式：

### 7.1 页面托管方式

优先采用“由 Koa 统一托管 Explorer 静态页”的方式，同时保留 `docs/` 中的文档入口说明。

原因如下：

- 这样可以保证启动一个本地服务后即可访问 Explorer，不需要额外感知多个端口。
- 自动打开浏览器时只需要打开一个地址，使用体验更直接。
- 若后续仍希望在 `docsify` 中保留入口，可在文档中增加跳转链接。

因此推荐结构为：

- `public/` 或新的静态资源子目录：实际 Explorer 页面资源
- `docs/`：文档说明与导航链接

如果实现中发现直接托管到 Koa 的成本高于预期，则回退到“API + docsify 双服务并行启动”方案，但这作为次优兜底，不作为首选。

### 7.2 元数据存放方式

推荐新增独立模块集中维护接口元数据，而不是分散在每个控制器文件内。

原因如下：

- 当前控制器文件大多以功能实现为主，不适合混入大量页面展示元数据。
- 集中维护便于页面统一读取，也便于后续逐步补全接口说明。
- 可以先覆盖常用接口，再逐步扩展到全量接口。

推荐结构示例：

- `src/config/api-explorer.ts` 或
- `src/constants/api-explorer.ts`

### 7.3 启动脚本方式

推荐新增统一启动脚本，负责：

- 检查本地服务地址
- 启动 API 服务
- 在适当时机自动打开浏览器

如果采用双服务模式，则该脚本还负责启动 docsify，并在文档服务就绪后打开 Explorer 地址。

## 8. 数据流设计

### 8.1 页面初始化

1. 浏览器打开 Explorer 页面。
2. 页面加载内置接口元数据，或从本地静态 JSON 拉取元数据。
3. 页面渲染接口分类、接口列表与默认表单。

### 8.2 请求发送

1. 用户填写路径参数、查询参数或请求体。
2. 页面对参数进行基础处理：
   - 替换路径模板中的参数占位符
   - 忽略空查询参数
   - 根据方法决定是否附带请求体
3. 页面通过 `fetch` 调用本地 API。
4. 页面记录请求开始时间与结束时间。
5. 页面渲染响应状态、耗时和响应内容。

### 8.3 错误处理

错误分为三类：

- 表单级错误：必填项为空、路径参数未填写
- 网络级错误：服务未启动、跨域错误、请求超时
- 业务级错误：接口返回非成功状态

页面应对策略：

- 表单错误在发送前阻止请求并给出明确提示
- 网络错误展示错误文案和原始异常信息摘要
- 业务错误仍展示状态码和响应体，方便调试

## 9. 关键设计决策

### 9.1 不采用完整 OpenAPI 的原因

本次不直接做 Swagger/OpenAPI，原因如下：

- 当前项目没有现成的接口 schema 体系，补齐成本高。
- 现有接口大量依赖路径参数和历史风格命名，机械生成 OpenAPI 价值有限。
- 用户当前诉求是“快速可测”，不是“标准可导出”。

后续若需要升级为 OpenAPI，可复用本次沉淀的接口元数据作为过渡基础。

### 9.2 不在 `test` 环境自动打开浏览器

测试环境必须禁用自动打开浏览器等副作用，原因如下：

- 避免 Jest 或其他测试命令产生额外 open handle。
- 保持 CI 环境纯净，避免图形相关命令失败。
- 与当前项目“测试环境禁用副作用逻辑”的约束一致。

### 9.3 自动打开失败不影响主流程

自动打开浏览器属于开发体验增强，不应影响 API 服务可用性。

因此设计上要求：

- 浏览器打开失败只打日志，不中断服务启动。
- Explorer 页面若无法自动打开，仍能通过本地地址手动访问。

## 10. 测试设计

### 10.1 测试目标

本次实现需要验证以下内容：

1. 接口元数据结构正确，能够覆盖页面渲染所需字段。
2. 请求 URL 拼装逻辑正确，能处理路径参数、查询参数和空值过滤。
3. 启动逻辑在非 `test` 环境下会触发自动打开浏览器。
4. 启动逻辑在 `test` 环境下不会触发浏览器打开。
5. 页面关键交互具备最小可用验证。

### 10.2 推荐测试拆分

#### 单元测试

重点覆盖：

- 接口元数据校验
- URL 构造函数
- 参数序列化逻辑
- 自动打开浏览器的条件判断

#### 集成测试

重点覆盖：

- 启动后 Explorer 静态资源可访问
- 至少 1 至 2 个接口可通过页面配置正确发起请求

#### 功能验证

手工验证以下流程：

1. 启动开发脚本
2. 浏览器自动打开 Explorer
3. 选择一个 `GET` 接口并填写参数
4. 成功看到响应结果
5. 选择一个 `POST` 接口并填写 Body
6. 成功看到响应结果或预期错误提示

### 10.3 Mock 原则

遵循当前项目测试约束：

- 不依赖真实浏览器 GUI，自动打开行为通过 mock 系统调用验证。
- 不依赖真实外部 QQ 音乐网络作为页面逻辑测试前提。
- 测试中对自动打开逻辑和静态资源逻辑做隔离验证，避免不稳定副作用。

## 11. 分阶段实施计划

### 阶段 1：创建 worktree 与脚手架

- 创建功能分支和独立 `git worktree`
- 在 worktree 中补充设计文档和实施计划
- 确认启动方式与静态资源承载位置

### 阶段 2：建立接口元数据层

- 新增集中式接口元数据定义
- 先覆盖常用高频接口
- 抽离 URL 构造与参数处理工具函数

### 阶段 3：实现 Explorer 页面

- 新增静态页面、基础样式与请求逻辑
- 渲染接口列表、参数表单、响应区
- 支持 `GET` 与 `POST` 两类基础请求方式

### 阶段 4：接入启动自动打开能力

- 新增开发启动脚本
- 在非测试环境自动打开 Explorer 地址
- 失败时记录日志但不阻塞主服务

### 阶段 5：补测试与回归

- 完成单元测试和必要的集成测试
- 运行 `lint`、`test` 和功能验证
- 修复发现的问题，直到满足发布标准

## 12. 风险与应对

### 风险 1：接口元数据维护成本上升

应对：

- 首版仅覆盖常用接口和高价值调试入口
- 采用集中式结构，降低查找和补充成本

### 风险 2：双服务模式导致启动复杂

应对：

- 首选单服务托管 Explorer
- 仅在必要时回退到双服务模式

### 风险 3：自动打开浏览器影响测试或 CI

应对：

- 明确以环境变量和运行模式控制副作用
- 测试环境中默认禁用自动打开能力

### 风险 4：页面功能过度膨胀

应对：

- 严格限定首版只做“选择接口、输入参数、发请求、看结果”
- 暂不加入历史记录、收藏夹、批量请求等附加功能
