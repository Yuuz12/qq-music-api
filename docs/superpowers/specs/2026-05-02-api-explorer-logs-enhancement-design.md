# API Explorer Logs 增强设计

## 1. 文档目标

本设计文档定义 `public/explorer/` 中 `Logs` 面板的一次结构化增强方案，目标是在不改动后端协议和主请求链路的前提下，将当前偏文本输出型的日志区升级为更易读、更易筛选、更易定位的调试日志面板。

本轮增强聚焦以下用户诉求：

1. 为日志增加更明确的视觉提示，包括 `emoji`、时间信息和状态颜色。
2. 为不同日志状态提供清晰的颜色区分，包括成功、失败和进行中。
3. 提供多种“快速定位”能力，包括点击条目看详情、关键词筛选和状态级快捷跳转。
4. 保持 Explorer 当前工具化布局，不引入新的前端框架，不改变 `/explorer/metadata` 接口。

## 2. 背景与现状

当前 Explorer 的日志相关文件如下：

- `public/explorer/index.html`
- `public/explorer/styles.css`
- `public/explorer/app.js`

当前 `Logs` 面板的实现特征如下：

1. 页面右侧仅保留一个 `pre#request-log-detail` 作为日志详情输出区域。
2. 所有请求日志会以纯文本拼接方式渲染在同一个文本块中。
3. 每条日志虽然包含时间、状态、耗时、请求体和响应摘要，但缺少结构化层级。
4. 用户只能通过滚动长文本查找目标记录，无法按失败状态、关键词或最新请求快速定位。

当前实现存在的主要问题如下：

- 日志是“全文本串联”，可读性弱。
- 请求量增加后，日志难以快速回看和排障。
- 最新请求、最近失败请求和当前查看详情之间没有明确区分。
- 缺少日志列表与详情的分离结构，不利于后续扩展。

## 3. 目标

本轮增强的直接目标如下：

1. 将日志区从单一 `pre` 文本块升级为“日志列表 + 日志详情”的双栏面板。
2. 给日志状态增加稳定的视觉语言，包括 `emoji`、颜色和状态文案。
3. 在日志卡片中突出显示时间、方法、状态、耗时和接口名。
4. 提供三类快速定位能力：
   - 点击日志条目查看详情
   - 关键词筛选
   - 状态快捷定位
5. 默认聚焦最新日志，且在用户未主动切换时自动跟随最新请求。
6. 保持 `Response` 面板只展示最近一次请求结果，`Logs` 面板负责会话轨迹查看，两者职责继续隔离。

## 4. 非目标

以下内容不属于本次增强范围：

- 修改请求发送逻辑或后端接口协议。
- 引入 React、Vue 或其他组件框架。
- 新增服务端日志采集或持久化存储。
- 新增日志分页、跨会话归档或导出能力。
- 新增折叠树、多标签日志页或复杂时间轴动画。

## 5. 方案选型

本次采用 `方案 B：双栏日志面板`。

### 5.1 方案 A：在现有文本日志上做轻量增强

- 继续保留单个 `pre`。
- 通过文本模板加入 emoji、时间和状态前缀。
- 顶部新增少量筛选按钮。

优点：

1. 改动小。
2. 风险低。
3. 上线速度快。

缺点：

1. 无法真正解决长日志定位问题。
2. 点击跳详情体验弱。
3. 结构上仍不适合后续扩展。

### 5.2 方案 B：日志列表 + 详情面板

- 左侧展示结构化日志条目列表。
- 右侧展示当前选中日志的完整详情。
- 顶部增加搜索和状态快捷筛选。

优点：

1. 完整覆盖“emoji + 时间 + 颜色 + 快速定位”的目标。
2. 可读性、可扫描性和排障效率明显提升。
3. 与当前 `Response / Logs` 双面板布局兼容性好。
4. 后续若要扩展复制、锚点和分组能力，结构基础已经具备。

缺点：

1. 需要同步调整 `index.html`、`styles.css` 和 `app.js`。
2. 日志状态需要增加更明确的前端选择和高亮逻辑。

### 5.3 方案 C：完整调试控制台

- 在方案 B 基础上继续加入折叠分组、锚点跳转、历史回放和复制能力。

优点：

1. 调试体验最完整。

缺点：

1. 范围过大。
2. 容易偏离“日志增强”主题。
3. 实现与测试成本高。

### 5.4 选择原因

选择方案 B 的原因如下：

1. 用户明确要求三类快速定位能力同时存在。
2. 方案 B 能在一次结构升级中同时满足信息密度与可操作性。
3. 当前 Explorer 已具备稳定的结果区布局，适合在 Logs 内部做双栏细化，而不是继续堆叠纯文本。

## 6. 信息架构

增强后 `Logs` 面板按如下顺序组织：

### 6.1 Header Summary

保留现有 `Logs` 标题，并新增以下摘要信息：

1. 当前会话日志总数
2. 失败日志数量
3. 最新日志时间

摘要信息用于让用户在不展开详情时也能快速判断当前会话状态。

### 6.2 Toolbar

日志工具条位于 `Logs` 标题下方，用于快速定位，包含：

1. 关键词搜索输入框
2. 状态快捷筛选按钮组
3. 快速跳转按钮

按钮集合如下：

- `全部`
- `仅失败`
- `仅进行中`
- `最近请求`
- `最近失败`

### 6.3 Log List

日志列表位于左侧，展示当前筛选结果中的日志条目卡片。每条卡片至少展示：

1. 状态 emoji
2. 时间
3. 请求方法
4. 接口名
5. 状态码或状态标签
6. 耗时
7. URL 简写或错误摘要

### 6.4 Log Detail

日志详情位于右侧，展示当前选中日志的完整信息，包括：

1. 基础头信息
2. 请求 URL
3. 请求体
4. 响应体或错误信息

详情区域继续使用代码块风格，但不再承担“日志列表”职责。

## 7. DOM 调整方案

### 7.1 `index.html`

当前 `section.workspace-log-card` 需要从单容器结构调整为以下结构：

1. 标题区
2. 日志摘要区
3. 日志工具条
4. 日志主体区
   - 左侧日志列表容器
   - 右侧日志详情容器

建议新增关键节点如下：

- `log-summary`
- `log-search-input`
- `log-filter-group`
- `request-log-list`
- `request-log-detail`
- `jump-latest-log`
- `jump-latest-error-log`

### 7.2 节点职责

各节点职责如下：

- `log-meta`：显示会话统计摘要，而不是仅显示条数。
- `log-search-input`：按接口名、URL、状态、错误信息筛选日志。
- `log-filter-group`：承载状态筛选和快捷跳转按钮。
- `request-log-list`：渲染结构化日志列表。
- `request-log-detail`：渲染当前选中日志的完整详情。

## 8. 前端状态与数据结构

### 8.1 现有日志数据

当前日志结构已经包含以下字段：

- `id`
- `timestamp`
- `endpointId`
- `endpointName`
- `method`
- `url`
- `requestBody`
- `status`
- `duration`
- `responsePreview`
- `errorMessage`

本轮不修改后端相关数据来源，也不强制变更该结构。

### 8.2 新增前端视图状态

前端状态需新增以下字段：

1. `activeLogId`
2. `logSearchKeyword`
3. `logStatusFilter`
4. `isAutoFocusLatestLog`

定义如下：

- `activeLogId`：当前在详情区展示的日志 ID。
- `logSearchKeyword`：日志搜索关键字。
- `logStatusFilter`：当前日志筛选状态，枚举为 `ALL | ERROR | PENDING | SUCCESS`。
- `isAutoFocusLatestLog`：用户未主动切换时，新增日志是否自动切换到最新。

### 8.3 派生状态

需要增加以下派生计算逻辑：

1. `visibleLogs`
2. `latestLog`
3. `latestErrorLog`
4. `logSummary`

规则如下：

- `visibleLogs` 由关键字和状态筛选共同决定。
- `latestLog` 为当前会话第一条日志。
- `latestErrorLog` 为当前会话中最新一条失败日志。
- `logSummary` 输出总数、失败数和最新时间。

## 9. 交互设计

### 9.1 默认行为

默认规则如下：

1. 当没有日志时，日志列表显示空态，详情区显示引导文案。
2. 当产生第一条日志时，自动选中该日志并展示详情。
3. 当用户未主动切换日志时，新请求产生后自动聚焦最新日志。
4. 当用户点击过历史日志后，`isAutoFocusLatestLog` 设为 `false`，后续新增日志不打断当前查看内容。

### 9.2 点击定位

日志卡片点击规则如下：

1. 点击任意日志条目，设置 `activeLogId`。
2. 详情区同步展示该日志的完整内容。
3. 当前选中日志在列表中使用高亮边框和背景区分。

### 9.3 关键词筛选

搜索输入框匹配以下字段：

1. `endpointName`
2. `url`
3. `status`
4. `errorMessage`
5. `responsePreview`

规则如下：

1. 搜索为空时不过滤。
2. 搜索使用大小写不敏感匹配。
3. 当搜索结果不包含当前选中日志时，自动将 `activeLogId` 切换到过滤结果第一项。
4. 若筛选结果为空，列表与详情同时回到“无匹配结果”空态。

### 9.4 状态快捷筛选

状态筛选规则如下：

1. `全部` 显示所有日志。
2. `仅失败` 显示 `error` 状态日志。
3. `仅进行中` 显示 `pending` 状态日志。
4. `SUCCESS` 状态由数字型 HTTP 状态码且 `< 400` 推导。
5. `ERROR` 状态包含：
   - `status === 'error'`
   - HTTP 状态码 `>= 400`

### 9.5 快速跳转

快捷跳转规则如下：

1. 点击 `最近请求`：
   - 选中最新日志
   - 列表滚动到对应条目
2. 点击 `最近失败`：
   - 若存在失败日志，选中最新失败日志并滚动定位
   - 若不存在失败日志，按钮禁用

## 10. 视觉设计

### 10.1 Emoji 规则

日志状态统一使用以下 emoji：

1. `⏳`：请求进行中
2. `✅`：请求成功
3. `❌`：请求失败

使用原则：

- emoji 仅作为辅助视觉锚点，不替代文字状态。
- 在列表卡片中优先出现在最左侧。
- 在详情区头信息中重复显示一次，增强当前状态识别。

### 10.2 颜色规则

状态颜色规则如下：

1. 进行中：蓝色系
2. 成功：绿色系
3. 失败：红色系

颜色使用位置如下：

- 状态徽标
- 日志卡片左侧强调线或边框
- 当前选中条目背景强调
- 快捷筛选按钮激活态

视觉原则：

1. 颜色区分应足够明显，但不破坏整体浅色工具风。
2. 日志详情区继续保持中性背景，避免正文难读。

### 10.3 时间展示

时间显示策略如下：

1. 列表卡片中显示 `HH:mm:ss`
2. 详情头信息中显示完整本地时间
3. Header Summary 中显示最近日志时间，便于快速判断会话活跃度

## 11. 详情区内容组织

详情区推荐按以下顺序输出：

1. 状态头信息
   - emoji
   - 方法
   - 接口名
   - 时间
   - 状态
   - 耗时
2. 请求信息
   - URL
   - Request Body
3. 响应信息
   - Response Preview
   - Error Message

详情区应保留代码块风格，但通过小标题和分段提高可读性。

1. `log-toolbar`
2. `log-search`

6. `log-item.is-active`

8. `log-item.success`
9. `log-item.error`
10. `log-detail-panel`

### 12.2 布局规则

日志主体区使用双栏布局：

1. 左侧日志列表约占 `42%`
2. 右侧日志详情约占 `58%`
3. 两栏都设置 `min-width: 0`
4. 两栏都在自身区域内滚动

### 12.3 响应式

在窄屏场景下：

1. Logs 主体区回退为上下堆叠
2. 列表在上，详情在下
3. 快捷按钮允许换行，但保持逻辑分组

## 13. 实现影响面

### 13.1 `public/explorer/index.html`

主要负责新增日志工具条、列表容器和详情容器。

### 13.2 `public/explorer/styles.css`

主要负责双栏布局、状态颜色、卡片样式和响应式规则。

### 13.3 `public/explorer/app.js`

主要负责：

1. 增加日志视图状态
2. 渲染结构化日志列表
3. 处理日志筛选
4. 处理当前日志选中
5. 处理最近失败与最近请求跳转
6. 在请求生命周期中驱动日志列表和详情联动

## 14. 风险与边界

主要风险如下：

1. 当筛选条件变化时，当前选中日志可能失效，需要正确回退。
2. 新日志插入头部后，列表滚动与详情选中逻辑需要保持一致。
3. 失败状态既可能来自 `fetch` 异常，也可能来自 HTTP 错误状态码，前端需要统一视觉语义。

边界原则如下：

1. 不新增日志持久化。
2. 不修改 `Response` 面板的数据职责。
3. 不将日志区扩展成完整 DevTools 控制台。

## 15. 测试策略

至少验证以下场景：

1. 无日志时，日志列表与详情显示空态。
2. 发送请求后，日志列表新增条目，详情自动选中最新日志。
3. 成功请求显示 `✅` 和成功颜色。
4. 失败请求显示 `❌` 和失败颜色。
5. 进行中请求显示 `⏳` 和进行中颜色。
6. 关键词筛选可命中接口名、URL 和错误文案。
7. 点击 `最近请求` 可定位到最新日志。
8. 点击 `最近失败` 可定位到最近失败日志，若无失败日志则按钮禁用。
9. 当前选中日志在筛选变化后若失效，会自动切换到可见列表第一项。

自动化验证建议如下：

- 更新 `tests/explorer.routes.test.ts` 中对静态 HTML 结构关键字的断言。
- 为日志渲染、筛选和定位逻辑补充前端纯逻辑测试。
- 保持现有 Explorer 路由和元数据测试继续通过。

## 16. 实施结论

本次 Logs 增强采用“结构化列表 + 详情面板”的双栏方案，在不改变主请求流程和后端协议的前提下，为 Explorer 增加更明确的视觉层次和更高效的日志定位能力。

实施阶段应优先保证：

1. 先完成日志列表与详情区的结构重建。
2. 再补齐 emoji、颜色和时间展示。
3. 最后接入关键词筛选、状态筛选和快捷跳转逻辑。
