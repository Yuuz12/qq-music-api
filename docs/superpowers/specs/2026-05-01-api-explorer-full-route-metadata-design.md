# API Explorer 全量路由元数据扩展 Spec

## 1. 文档目标

本 Spec 定义 `qq-music-api` 当前 `API Explorer` 的下一步扩展方案：在保持现有页面交互与请求能力不大改的前提下，将 `src/routes/router.ts` 中已挂载的全部路由纳入 Explorer 元数据体系，做到“全部路由可见、可选、可调试”。

本次目标不是把每一个接口都打磨成完整的 OpenAPI 文档，而是建立一套“全量覆盖 + 分层精细化”的元数据组织方式，让 Explorer 从“少量精选接口”升级为“覆盖整个项目路由面”的开发调试工具。

## 2. 背景与上下文

当前项目已经完成首版 Explorer 基础能力：

- 启动开发环境后可自动打开 `Explorer`
- `Explorer` 页面已支持接口选择、参数输入、请求发送与响应展示
- 后端已提供 `/explorer/metadata` 元数据接口
- 当前元数据文件为 `src/config/apiExplorer.ts`

当前主要限制：

- Explorer 只覆盖了少量高价值接口，当前约为 6 个
- `router.ts` 中已挂载接口数量明显更多，当前绝大多数接口在 Explorer 中不可见
- 现有元数据完全手工维护，若直接扩到全部路由，维护成本会快速上升

因此本次工作的核心问题不是“能不能继续往数组里加对象”，而是“如何让全部路由被覆盖，同时避免元数据文件变成难维护的大清单”。

## 3. 目标

本次工作的目标如下：

1. 让 `router.ts` 中全部已挂载接口都能出现在 Explorer 中。
2. 保留当前高频接口的精细化元数据能力。
3. 对低频或复杂接口提供最小可用元数据，确保用户至少能看到路径、方法和基础参数。
4. 为元数据覆盖范围补充自动化测试，防止后续新增路由后 Explorer 漏配。
5. 保持现有 Explorer 页面协议兼容，避免重写前端交互。

## 4. 非目标

以下事项不在本次工作直接承诺范围内：

- 为所有接口补齐完整请求/响应 schema
- 自动推断所有 query 参数和 body 参数的真实业务语义
- 为每个接口都提供精细中文描述、默认值和示例数据
- 将 Explorer 升级为 OpenAPI 或 Swagger 体系
- 变更现有控制器、服务层或路由行为

## 5. 方案选型

本次采用 `方案 B：全量路由覆盖 + 分层精细化`。

### 5.1 备选方案

#### 方案 A：纯手工全量补齐

- 直接把所有路由都手工补进静态元数据数组

优点：

- 可完全自定义每个接口的展示细节

缺点：

- 工作量大
- 容易出现重复、遗漏和后续维护负担

#### 方案 B：全量覆盖 + 分层精细化

- 先为全部路由生成最小可用元数据
- 再对高频接口叠加精细配置

优点：

- 能快速覆盖全部路由
- 同时保留高价值接口的体验质量
- 兼顾可维护性与可扩展性

缺点：

- 部分低频接口首版的说明信息会比较基础

#### 方案 C：纯自动推导

- 从 `router.ts` 自动推导全部元数据，不再维护手工配置

优点：

- 理论上维护成本最低

缺点：

- 当前项目很多真实参数来自 `query` 或 `body`
- 仅靠路径模板无法准确表达接口使用方式
- 生成结果可用性有限

### 5.2 选择原因

选择方案 B 的原因如下：

- 既满足“全部路由都进入 Explorer”的明确需求
- 又不要求一次性为所有接口补完高质量说明
- 和当前已有的首版 Explorer 结构兼容，能在最小改动下继续演进

## 6. 总体设计

整体设计拆成三个层次：

1. 路由基础信息层
2. 手工覆盖配置层
3. 最终元数据组装层

### 6.1 路由基础信息层

这一层负责表达“项目里有哪些已挂载路由”。

来源有两种可选方式：

- 直接在配置文件中维护一个与 `router.ts` 对齐的基础路由清单
- 从 `router.ts` 中抽出共享常量，再由路由和 Explorer 共用

本次推荐优先采用“在 `apiExplorer.ts` 中维护基础路由清单”的方式，不对现有路由注册结构做大改。

基础路由信息至少包含：

- `method`
- `path`
- `name`
- `category`

### 6.2 手工覆盖配置层

这一层负责为高价值接口补充更丰富的配置，例如：

- 更友好的描述
- 更准确的参数标签
- 默认值
- `POST` 请求体示例
- query 参数说明

适用对象：

- 当前已经接入的高频接口
- 明显需要默认值才能方便调试的接口
- 路径复杂或命名不直观的接口

### 6.3 最终元数据组装层

这一层负责把“基础路由信息”和“手工覆盖配置”合并成 Explorer 实际消费的数据结构。

组装规则如下：

1. 先拿到全部基础路由条目。
2. 从路径模板中自动提取 `pathParams`。
3. 为没有手工配置的接口生成最小元数据。
4. 对存在手工覆盖配置的接口，用精细信息覆盖默认项。
5. 输出统一结构给 `/explorer/metadata`。

## 7. 元数据设计

### 7.1 最小可用元数据

对于非重点接口，最少生成以下字段：

- `id`
- `name`
- `category`
- `description`
- `method`
- `path`
- `pathParams`

其中：

- `id` 采用稳定命名规则生成
- `name` 默认使用接口名
- `category` 按模块分组
- `description` 使用简短占位说明，例如 “Call `<routeName>` endpoint.”

### 7.2 自动推导的 `pathParams`

对于路径形如：

- `/getSongInfo/:songmid?/:songid?`
- `/getSingerAlbum/:singermid?/:limit?/:page?`

Explorer 可自动提取：

- `songmid`
- `songid`
- `singermid`
- `limit`
- `page`

并生成最小字段对象：

- `key`
- `label`
- `required`

其中 `?` 标记的参数默认为非必填。

### 7.3 手工精修的 query/body 配置

对以下场景保留手工配置能力：

- query 参数较多的搜索类接口
- 需要示例 body 才能正确调试的 `POST` 接口
- 参数名含义不明显的接口

这意味着：

- 高价值接口继续手工精修
- 普通接口先只依赖路径自动推导

## 8. 分类设计

为了避免全部接口堆在一个列表中，本次需要统一分类规则。

推荐分类如下：

- `User`
- `Search`
- `Song Lists`
- `Song`
- `Singer`
- `MV`
- `Album`
- `Radio`
- `Digital Album`
- `Rank`
- `Recommend`
- `Ticket`
- `Common`
- `Batch`

分类规则优先基于接口语义，而不是纯文件路径名称。

## 9. 关键设计决策

### 9.1 不强行自动推导 query/body

不自动推导 query 参数和 body 参数，原因如下：

- 当前控制器取参方式不统一
- 有的取 `ctx.query`
- 有的取 `getTypedQuery`
- 有的取 `ctx.request.body`
- 单靠静态路径无法可靠判断其完整参数结构

因此本次只自动推导 `pathParams`，其余参数继续由手工配置补充。

### 9.2 不改现有 Explorer 前端协议

Explorer 页面已经可以消费当前元数据结构，因此本次不改前端协议，只扩展数据规模。

这可以保证：

- 首版页面逻辑不需要重写
- 测试影响面更小
- 扩展完成后立即可用

### 9.3 元数据覆盖测试作为防回归门禁

本次必须增加“全部路由都被 Explorer 收录”的测试。

该测试作用如下：

- 新增路由时，若忘记更新 Explorer 元数据，会立刻在测试中暴露
- 避免后续维护中再次退化为“只覆盖少数接口”

## 10. 测试设计

### 10.1 新增测试目标

本次至少补充以下测试：

1. `router.ts` 中的全部已挂载路由都能在 Explorer 元数据中找到对应项。
2. 自动生成的 `pathParams` 能正确识别可选与非可选参数。
3. 手工覆盖配置仍能优先生效，不会被默认生成逻辑覆盖掉。
4. `/explorer/metadata` 返回的数据条目数与路由条目数保持一致或更高。

### 10.2 测试策略

采用“结构断言 + 覆盖断言”的方式：

- 结构断言：验证元数据字段存在且格式正确
- 覆盖断言：验证每个已挂载路由都有映射元数据

### 10.3 边界情况

需要覆盖以下边界情况：

- 含多个可选路径参数的接口
- 无参数接口
- `POST` 接口
- 同模块多个相似接口的 `id` 稳定性

## 11. 分阶段实施计划

### 阶段 1：抽象基础路由清单

- 整理 `router.ts` 中全部路由
- 建立统一的基础路由描述结构

### 阶段 2：实现自动推导与合并逻辑

- 新增 `pathParams` 自动提取
- 合并手工覆盖配置与默认配置

### 阶段 3：补齐分类与说明

- 为全部路由指定分类
- 对重点接口继续保留精细配置

### 阶段 4：补测试与回归

- 新增全量覆盖测试
- 运行 `lint`、`test`、功能验证

## 12. 风险与应对

### 风险 1：元数据文件体积继续增长

应对：

- 通过“基础路由清单 + 手工覆盖配置”拆层
- 避免所有接口都写成重复的大对象

### 风险 2：分类或命名不一致

应对：

- 明确固定分类集合
- 用统一命名规则生成 `id`

### 风险 3：覆盖测试与真实路由结构不一致

应对：

- 测试直接以 `router.ts` 当前已挂载路由为基准
- 不依赖人工统计数量
